0. 引言：内核之上，程序如何真正跑起来

内核把自己立起来、接管了硬件之后，一个真正的用户程序要在它之上跑起来，中间还隔着厚厚的一叠系统软件。从最贴近硬件的板级适配与硬件抽象层，到驱动各类设备的子系统、承载数据的文件系统与网络协议栈，再到内核向用户态敞开的系统调用接口、包装这些接口的 C 运行时与标准库、把源码变成机器码的编译器与即时编译，直至跨操作系统运行程序的兼容层、隔离整套系统的虚拟化与容器，最后是把这一切裁剪、打包成一个可发布系统的发行版构建——这一叠，正是本篇要逐层拆开的对象。

走法是自底向上：从离硬件最近的一层起步，一路向上抵达用户能直接触到的应用与发行版。每一层都落到两件事——既看清它”是什么、为何如此、源码里如何实现”，又能据此自己写出一个同生态位的替代。系统调用一节会把三百余个 Linux 系统调用逐个讲到功能与实现；标准库一节会把所有 libc 实现的所有头文件、所有函数列全，连 Rust 的 core/std 也一并铺开。粒度刻意做到细，便于既通读、又随时回来查。

层次自下而上依次是：板级适配与 HAL（§1）、外设驱动（§2）、文件系统（§3）、网络栈（§4）、系统调用机制与架构 ABI（§5）、Linux 系统调用全谱与专有高级接口（§6）、C 运行时启动链（§7）、libc 与标准库全谱（§8）、动态链接运行时与 vDSO（§9）、编译器后端与即时编译（§10）、跨操作系统运行（§11）、虚拟化与容器（§12）、系统裁剪与发行版（§13），最后是资源精读、词典与思考题（§14–§16）。

1. 板级适配与 HAL

最贴近硬件的一层是硬件抽象层（HAL）。”HAL”这个词在两个层级被复用，目标与抽象对象完全不同，必先分清：

维度 OS 级 HAL（代表 polyhal） MCU 级 HAL trait（代表 embedded-hal）
抽象对象 CPU 特权机制：MMU/页表、trap/中断、定时器、多核启动、percpu 板上外设总线：GPIO/I2C/SPI/PWM/延时
跨的维度 跨指令集（rv/x86/aa/la），同一份内核代码 跨芯片厂商 PAC（STM32/nRF/RP2040…），同一指令集
谁实现 HAL crate 自身用 cfg(target_arch) 分文件实现 各芯片 HAL crate（如 stm32f4xx-hal）impl trait
谁消费 内核（arceos/StarryOS 风格的 Unikernel/宏内核） 驱动 crate（设备驱动、传感器驱动）
形态 一组具体 struct + 自由函数 一组 trait（OutputPin/I2c/SpiBus）
类比 Linux arch/ + asm/ drivers/ 子系统的 bus_type 抽象

polyhal 统一的是”同一份内核代码跑在 rv/x86/aa/la 四种 CPU 上”，embedded-hal 统一的是”同一份驱动代码跑在 N 种 MCU 上”。两者正交、可叠加——一颗 rv SoC 的内核既可用 polyhal 抽 CPU，又可在驱动层用 embedded-hal trait 抽外设。下面两层都做到既会用、又会写。

1.1 polyhal——OS 级跨架构 HAL（会写：内部如何统一四架构）

polyhal（Byte-OS，v0.4.0）是一个 cargo workspace，含五个 crate：polyhal（核心，arch/components/pagetable/mem）、polyhal-boot（启动汇编 _start + percpu/页表/MMU 初始化 + define_entry!）、polyhal-trap（trap 向量 + TrapFrame + TrapType）、polyhal-macro（过程宏）、example（四架构通用示例内核）。

它统一了什么。 components/mod.rs 列出八个跨架构组件，每个用 define_arch_mods!() 按 target_arch 分文件实现：common（PageAlloc 注入页分配器 + get_cpu_num()）、mem（内存屏障 + FDT 内存区发现）、instruction（shutdown()/ebreak()）、irq（中断开关 + IRQVector）、kcontext（内核线程上下文 KContext + context_switch）、timer（current_time() + set_next_timer）、multicore（boot_core 拉起从核）、percpu（每核私有数据）；另加 pagetable（MMU 统一）与 debug_console（rv 走 sbi_rt::legacy::console_putchar）。

统一的三大机制（会写的关键）。 其一，define_arch_mods!() 宏（polyhal-macro/src/lib.rs:64）对每个组件目录生成四个 #[cfg(target_arch="…")] mod xxx; pub use xxx::*;，编译期只编入当前架构那一份——是编译期单态而非 trait object，零运行时分发开销。其二，pub_use_arch! 把架构私有符号重导出为统一名。其三，cfg_if! 在同一函数体内按架构切不同指令（读 thread pointer：x86 rdmsr(IA32_GS_BASE) / rv mv gp / aa mrs TPIDR_EL1 / la move $r21）。

MMU/页表统一（pagetable/mod.rs）：对外是 PageTable 与 RAII 的 PageTableWrapper（Drop 时 release() + frame_dealloc），统一操作 map_page/map_kernel/unmap_page/translate/release。架构差异藏在常量里——PAGE_LEVEL（Sv39=3 级 / x86 4 级），map_page 用 if Self::PAGE_LEVEL == 4 多走一级；pn_index(n) = (raw>>(12+9*n)) & 0x1ff 是 rv Sv39/Sv48 通用索引公式。MappingFlags 是架构无关的语义位（P/U/R/W/X/A/D/G/Device/Cache 及组合），各架构用 From<MappingFlags> for PTEFlags 翻译成硬件位。启动页表 init_boot_page_table 直接造 1 GB 大页恒等映射 + 高半区带全局位（内核高地址 VIRT_ADDR_START=0xffff_ffc0_0000_0000），再写 satp 开 Sv39。

trap 统一（polyhal-trap）：TrapType 是架构无关的语义枚举（Breakpoint/SysCall/StorePageFault/Timer/…）；用户用 #[polyhal::arch_interrupt] 标注一个 fn(&mut TrapFrame, TrapType)，宏把它 #[export_name="_interrupt_for_arch"] 焊到各架构 trap 汇编的回调点——内核只写一份中断处理逻辑。TrapFrameArgs 用 SEPC 等枚举索引跨架构访问寄存器，ctx.syscall_ok() 跨架构”跳过 ecall 指令”。

启动序（ctor.rs，这是 BSP 启动序的核心）：定义七级构造器优先级，linker section ph_init 收集所有 ph_ctor! 注册的初始化函数按级跑——主核 Cpu → Platform → HALDriver →（可选拉从核）→ KernelService → Normal → 跳内核。rv 落地是 rust_main：clear_bss → init_dtb_once → set_local_thread_pointer → init_cpu → ph_init_iter(Cpu) → parse_system_info → ph_init_iter(Platform/HALDriver) → call_real_main。定时器正是用 ph_ctor!(ARCH_INIT_TIMER, CtorType::Platform, init) 挂进启动序的——这就是”BSP 三件套之 tick”的注册点。

percpu（每核私有数据）：#[percpu] 宏把静态放进 percpu linker section 包成 PerCPU<T>，运行时为每核 alloc 副本、copy_nonoverlapping 初始化、写架构 thread-pointer 寄存器（rv 用 gp、x86 用 gs:8 间接、aa 用 TPIDR_EL1、la 用 $r21）。

会用 polyhal：内核侧用 define_entry! 给出入口、#[arch_interrupt] 给出中断回调、向 common::init 注入一个 PageAlloc 页分配器即可；其余 CPU/MMU/timer/多核全部由 polyhal 按目标架构编译期生成。换言之，”用 polyhal 写内核 = 写四份架构无关的回调 + 注入一个分配器”。

它没统一什么（诚实边界，自己造 HAL 必须知道）：外设驱动全不在 polyhal（只给靠 SBI legacy putchar 的 DebugConsole，真实串口/PCI 留给上层）；中断控制器在 rv 端是空壳——irq/riscv64.rs 的 irq_enable/irq_disable 直接 log::warn!("irq not implemented")，只实现了 int_enable=set_sie 这种全局 S 态总开关，PLIC/外部中断号管理、AIA(APLIC+IMSIC) 完全没做；时钟频率 CLOCK_FREQ=12500000 是 QEMU virt 硬编码常量而非运行时读 FDT；大页只有 4 KB；map_kernel 内核空间页表共享标着 TODO。这条 FDT 运行时发现 vs 编译期 board 常量（boards/qemu.rs vs boards/k210.rs）的二分，与 KuSBI 的两种 Platform Mode 是同一设计哲学。

1.2 embedded-hal v1.0——MCU 级外设 trait 抽象（会用为主，会写其落地）

embedded-hal（v1.0.0，2024 稳定）是 Rust 嵌入式生态最广泛的 trait 集合，一个仓库含九个 crate：embedded-hal（阻塞式核心 trait：delay/digital/i2c/pwm/spi）、embedded-hal-async（同名 trait 的 async fn 版）、embedded-hal-nb（nb would-block 风格）、embedded-hal-bus（总线共享的具体实现，唯一含实现的 crate）、embedded-io[-async/-adapters]（Read/Write/BufRead/Seek——UART/串口 1.0 后归这里）、embedded-can。MSRV 1.81。

核心 trait 逐个穷举（1.0 实际内容，已删 ADC/serial）：

  • digital（GPIO）：OutputPin（set_low/set_high/set_state(PinState)）、StatefulOutputPin（is_set_high/is_set_low/toggle）、InputPin（is_high/is_low）；PinState{Low,High} + ErrorType 关联类型 + ErrorKind。
  • i2c：I2c<A=SevenBitAddress> 含 read/write/write_read/transaction(&mut [Operation])；Operation{Read(&mut[u8]), Write(&[u8])}；地址 SevenBitAddress=u8/TenBitAddress=u16；ErrorKind（Bus/ArbitrationLoss/NoAcknowledge/Overrun/Other）。
  • spi（1.0 标志性的 SpiBus/SpiDevice 分裂）：SpiBus<Word=u8> 是整条总线 read/write/transfer/transfer_in_place/flush（不管片选）；SpiDevice<Word=u8> 是总线上的一个设备，核心是 transaction(&mut [Operation])（自动拉低/拉高 CS + 锁总线）；Mode{polarity, phase} 即 CPOL/CPHA。
  • pwm：SetDutyCycle（max_duty_cycle() + set_duty_cycle(u16) + 默认 set_duty_cycle_percent 等）——只设占空比，频率属硬件配置留给芯片 HAL。
  • delay：DelayNs（delay_ns 核心 + 默认 delay_us/delay_ms）。

SpiBus/SpiDevice 为何分裂（会用的关键认知）：0.2 时代 SPI 是一堆 FullDuplex/Write trait 且不管 CS、无法安全共享一条总线。1.0 拆成 SpiBus（整线）+ 新增 SpiDevice（带 CS 的单设备）。驱动应当写到 SpiDevice——这样多个驱动能共享一条物理 SPI 总线、各自有片选；SpiBus 留给独占总线场景。这个分裂的落地在 embedded-hal-bus：它把一条 SpiBus/I2c 包装成多个可共享的设备，提供六种并发策略（exclusive/refcell 单线程/mutex 多线程/critical_section 跨中断/atomic/rc）——分裂之后总线共享策略可独立选择而驱动代码不变。这正是”面向 trait 写驱动”的威力：一个温度传感器驱动写成 fn new(i2c: impl I2c)，就能跑在任何 impl 了 I2c 的芯片上。

1.0 相对 0.2 的删改（会用时易踩）：删 ADC（OneShot/Channel 不实用）、删 serial/UART（改用 embedded-io 的 Read/Write）、删 IoPin（运行时切换输入输出，不实用）、SPI 统一加分裂、所有方法 fallible 化（-> Result<_, Self::Error> + ErrorType）、DelayMs+DelayUs 合并为 DelayNs、阻塞与 nb 风格分家。

1.3 svd2rust——从 SVD 到 PAC 的寄存器级 BSP 自动化

svd2rust（v0.37.1，rust-embedded Tools team）把芯片厂商发布的 CMSIS-SVD（XML，描述每个外设的寄存器地址/字段/位）生成为类型安全的 PAC（Peripheral Access Crate）——把”裸地址 + 位操作”变成 peripherals.GPIOA.odr.modify(|_, w| w.odr5().set_bit()) 这种编译期检查的 API。

会用：svd2rust -i STM32F30x.svd 生成未格式化的 lib.rs，再用 form 工具拆分目录 + cargo fmt。--target 选 cortex-m（默认）/msp430/riscv/xtensa-lx/none，不同 target 生成不同的中断与启动胶水。cortex-m target 额外产出 build.rs（放置链接脚本 device.x）与 device.x（把所有中断 handler 弱别名到 DefaultHandler）。

会写（生成器内部）：generate/device.rs 生成顶层 Peripherals::take()（单例，保证寄存器块唯一所有权）；peripheral.rs 生成每个外设的 #[repr(C)] RegisterBlock（按 offset 排布）；register.rs 生成每个寄存器的 R(read)/W(write) proxy 与字段 reader/writer；generic.rs 提供体积无关的 Reg<REG> 通用 .read()/.write()/.modify() 原语；interrupt.rs 生成 enum Interrupt + 向量表。链路定位：SVD（厂商）→ svd2rust → PAC → 芯片 HAL crate（impl embedded-hal trait）→ 驱动 crate，svd2rust 站在最底层，是寄存器级的 BSP 自动化。

1.4 cortex-m 与 riscv——指令集级 CSR 与中断原语

这两个 crate 在 PAC 之下，给”指令集本身”（而非某颗芯片的外设）做抽象，是 polyhal 的 arch/ 层在 MCU 世界的等价物。

cortex-m（v0.7.7）含 cortex-m/cortex-m-rt（启动）/cortex-m-semihosting 等。它抽象 ARM 架构定义的核内系统外设：nvic（中断控制器）、scb（系统控制块）、syst（SysTick 定时器）、mpu（内存保护）、sau（TrustZone）、dwt/itm（调试 trace）、fpu；CPU 寄存器 control/primask/basepri/msp/psp 等；NVIC API（request/mask/unmask/set_priority/pend，泛型 <I: InterruptNumber>）；临界区 interrupt::disable()（关 PRIMASK）/free(|cs| …)；裸指令 nop/wfi/wfe/dsb/dmb/isb。

riscv（v0.16.0，七子 crate）含 riscv（CSR 核心）/riscv-rt（启动）/riscv-peripheral（CLINT/PLIC）/riscv-semihosting 等。register/ 约六十个文件覆盖 M 态与 S 态全套 CSR：mstatus/mie/mtvec/mepc/mcause/misa/mhartid/medeleg/mideleg、PMU 计数器、PMP（pmpaddrx/pmpcfgx）、AIA 相关（miselect/mtopi）、S 态镜像（satp/scause/stvec/sie）。关键是 riscv-peripheral——polyhal 缺的那块：aclint/{mtimer,mswi,sswi} 是 CLINT/ACLINT（机器定时器 + 软件中断/IPI 硬件），plic/{enables,pendings,priorities,claim,threshold} 是 PLIC 全套（使能/pending/优先级/claim-complete/阈值），hal/aclint.rs 还把 MTIMER 包成 embedded-hal 的 DelayNs 桥接两层 HAL。

横向看：cortex-m 的中断控制器 NVIC 在核内、紧耦合、硬件优先级抢占；rv 的 PLIC 在核外、由 riscv-peripheral 独立抽象，加 CLINT 定时器；临界区前者用 PRIMASK/BASEPRI、后者用 sstatus.SIE/mstatus.MIE。这正是 NVIC 与 CLINT→ACLINT、PLIC→APLIC+IMSIC 演化的 Rust 落地。

1.5 设备树在 probe 中的角色

板级适配的核心问题是”一块板子几十种外设，OS 怎么知道它们在哪、怎么用”。答案是设备树（DT）描述硬件 + 驱动框架按 compatible 匹配并 probe。链路是：DTB 描述 → 驱动核心扫描每个节点的 compatible → 在已注册驱动的 of_match_table 找匹配 → 命中则调 driver->probe(dev) → probe 内 ioremap 寄存器、request_irq、注册 fd/sysfs。DT 节点 compatible="vendor,foo-uart"; reg=<…>; interrupts=<…>; 中，reg 给寄存器基址、interrupts 给中断号与中断控制器 phandle。

DT 在三层 HAL 里角色不同：polyhal 启动期 init_dtb_once/parse_system_info 读内存区、get_fdt().all_nodes() 遍历 compatible 发现设备，但它不做驱动匹配、只把 FDT 暴露给上层；embedded-hal 的 MCU 世界通常无 DT（资源固定，PAC 编译期固化地址），对应 polyhal 的编译期 board 常量路径；Linux 风内核里 DT 是 probe 的输入，compatible 字符串驱动整个匹配（§2 详述）。x86 服务器用 ACPI（AML 字节码），rv/aa 嵌入式用 DT（静态 DTB），rv 两套并存。

1.6 BSP 三件套与板级适配清单（会用：把内核搬到新板子）

“把一个 HAL/内核搬到新板子”需要适配的最小集合：

件 polyhal 落点 embedded-hal 生态落点
heap / 页分配 注入 PageAlloc（common::init） linked_list_allocator + #[global_allocator]
串口 / console DebugConsole::putchar（rv 走 SBI legacy） 芯片 HAL 的 UART impl embedded-io::Write
tick / timer ph_ctor!(ARCH_INIT_TIMER, …) + set_next_timer（rv 走 sbi_rt::set_timer） SysTick（cortex-m）/ CLINT MTIMER（riscv-peripheral）

三件套之外的进一步清单：① 时钟频率（polyhal CLOCK_FREQ 常量，换板必改；真实 SoC 需配 PLL/时钟树）；② pinmux 引脚复用（polyhal 完全不管，MCU 侧由芯片 HAL 的 into_alternate() 处理、DT 侧用 pinctrl binding——这是 OS HAL 与 MCU HAL 的分工边界）；③ 中断控制器适配（polyhal rv 端是空壳，真实板子要接 PLIC 或 APLIC+IMSIC；cortex-m 用核内 NVIC 免适配）；④ 内存布局（VIRT_ADDR_START、链接脚本、cortex-m 的 memory.x）；⑤ 启动序常量（boot hart id、栈大小、SUM 位——特权架构 1.10 的 SUM 与 1.9.1 的 PUM 语义相反，ISA 版本差异也是适配点）；⑥ 设备发现策略二选一（运行时 FDT vs 编译期 board 常量）。

整条栈自底向上是：硬件 → 指令集抽象（cortex-m/riscv，对应 polyhal 的 arch/）→ PAC（svd2rust 生成）→ 芯片 HAL crate（impl embedded-hal trait）→ 驱动/应用 crate。OS 路线（polyhal）是另一条平行栈：硬件 → polyhal（CPU/MMU/trap/timer/percpu 跨指令集）→ 内核。两条栈在”指令集抽象”层概念对应。自己造 HAL 的取舍尽在其中：要跨指令集跑同一份内核，学 polyhal 的编译期单态 + 语义化 flag + 构造器启动序；要跨芯片跑同一份驱动，学 embedded-hal 的 trait + bus 共享策略；而 PLIC/时钟树这类”polyhal 留白”的真实板级细节，恰是 BSP 适配的主战场。

2. 外设驱动

驱动是内核与设备之间的翻译层。Linux 把它组织成一套统一模型——device / driver / bus 三元组，架在 kobject/sysfs 对象基座上——再在其上长出八大子系统。本章既拆这套模型的源码实现，又逐个看八大子系统各自怎么搭，最后看驱动如何跨操作系统复用。这是 KuOS 若要兼容 Linux 驱动必须复刻的全部。

2.1 device / driver / bus 三元组与 kobject/sysfs 基座

整套模型一句话：device（设备实例）/ driver（驱动）/ bus（总线，定义匹配与探测策略）三元组，加 class（功能视角，第四元），全部挂在 kobject 树上、镜像为 sysfs。

struct device 的第一个字段就是 struct kobject kobj——kobject 提供三件事：sysfs 目录节点、kref 引用计数（get_device/put_device）、parent 指针构成 /sys/devices/... 的设备拓扑。device 还含 bus（挂在哪条总线）、driver（绑到哪个驱动，NULL 即未绑）、driver_data（dev_set/get_drvdata 存私有数据）、mutex（即 device_lock，序列化对 ->driver 的操作）。

总线注册时建三个 kset（同类 kobject 的集合 + uevent 策略）：/sys/bus/<name>、/sys/bus/<name>/devices、/sys/bus/<name>/drivers。一个关键设计是 struct bus_type 现在是只读的外部句柄，真正可变的内部状态在 struct subsys_private（含那三个 kset、klist_devices、klist_drivers、drivers_autoprobe 开关、通知链）——bus_to_subsys() 把 bus_type* 映射到 subsys_private* 并加引用，所有内部操作先过这步。这是相对早期”bus_type 直接含可变字段”的重构，目的是外部接口 const 化 + 引用计数安全。

绑定发生时建立双向 symlink：/sys/bus/<b>/drivers/<drv>/<dev>（驱动管的设备）与 /sys/devices/.../<dev>/driver（设备的驱动）互指；module.c 另建 driver/module 链接把驱动与它的 .ko 关联起来。一个核心洞察是：sysfs 不是独立的文件系统数据，而是 kobject 树的镜像视图；kobject_uevent(&dev->kobj, KOBJ_ADD/BIND/UNBIND/REMOVE) 是内核到用户态 udev 的唯一热插拔通道。

bus 与 class 正交：bus 按”挂在哪条物理/逻辑总线”分类（platform/pci/i2c/usb），class 按”功能用途”分类（net/block/input/tty），一个 device 同时属于一条 bus 与（可选）一个 class，分别在 /sys/bus/*/devices/ 和 /sys/class/*/ 出现。

2.2 probe / remove 全链路与延迟探测

模型的核心是对称的两条入口在 bus 处汇合——新设备找所有驱动，新驱动找所有设备。

注册设备 device_add(dev)：分配 dev->p → 挂 sysfs 拓扑 → 建 uevent/class 属性 → bus_add_device（挂 klist_devices + symlink）→ 加电源管理链 → kobject_uevent(KOBJ_ADD) → fw_devlink_link_device（建供应商/消费者依赖图）→ bus_probe_device（触发探测）。

注册驱动 driver_register(drv)：检查总线已注册、重名检测 → bus_add_driver（分配 driver_private、初始化此驱动的 klist_devices、挂进 /sys/bus/<b>/drivers/<drv>、若 drivers_autoprobe 则 driver_attach 扫描已有设备）→ module_add_driver 建 /sys/module 链接。

匹配只有一个入口：driver_match_device(drv, dev) = drv->bus->match ? drv->bus->match(dev, drv) : 1（无 match 默认匹配）。返回值语义：>0 匹配、0 不匹配、-EPROBE_DEFER 延迟、<0 其他错误。

真正探测的主链是 driver_probe_device → __driver_probe_device → really_probe：检查 suspend 期全延迟标志 → device_links_check_suppliers（供应商未就绪即 -EPROBE_DEFER）→ device_set_driver（设 dev->driver）→ pinctrl_bind_pins → dma_configure → driver_sysfs_add（建 symlink）→ call_driver_probe（总线级 probe 优先于驱动 probe：dev->bus->probe ?: drv->probe）→ device_add_groups → driver_bound。绑定成功的 driver_bound：把设备挂进驱动的管辖表 → driver_deferred_probe_trigger（唤醒其他在等的延迟设备）→ kobject_uevent(KOBJ_BIND)。

延迟探测（deferred probe） 解决拓扑序依赖：当一个驱动 probe 时发现依赖的 GPIO/clk/regulator 控制器还没探测好，它返回 -EPROBE_DEFER，设备被挂到 deferred_probe_pending_list；而任何一次成功绑定都会把整张 pending 表 splice 到 active 表并 queue_work 重试——所以依赖一旦满足就连锁推进。内核启动末尾 late_initcall 使能并两轮触发，超时后对仍 pending 的设备告警，/sys/kernel/debug/devices_deferred 可查。一条铁律（kernel.org 文档强调）：-EPROBE_DEFER 要尽早返回，且不得在已注册子设备之后返回，否则无限 probe 循环。

会用层面，手动绑定走 sysfs：echo <dev> > /sys/bus/<b>/drivers/<drv>/bind（对应 unbind）；写设备的 driver_override 可强制它只匹配指定驱动。

2.3 platform 总线与四级匹配

platform 总线承载所有”非自描述、靠固件描述”的 SoC 片内设备，其 platform_match 是四级优先级：① driver_override（最高）→ ② OF/设备树匹配（比对设备 of_node 的 compatible 与驱动 of_match_table，命中后 data 即驱动私有 match data）→ ③ ACPI 匹配（比 _HID/_CID 与 acpi_match_table）→ ④ platform_device_id 表（name 精确）→ 兜底设备名等于驱动名。MODULE_DEVICE_TABLE(of/acpi/platform, …) 把这些表导出到模块的别名段，depmod 生成 modules.alias，udev 据 uevent 的 MODALIAS= 自动 modprobe 对应 .ko——这就是”插上设备自动加载驱动”的机制。

注册一个 platform 驱动只需 module_platform_driver(my_driver) 宏（底层 module_init/exit 包 __platform_driver_register），驱动写 .probe(pdev) 即可；platform 设备则由 of_platform_populate 从 DTB 解析生成、或 platform_device_register 手动注册。

2.4 模块 .ko 加载

普通驱动用总线宏（module_platform_driver/module_pci_driver/module_i2c_driver），底层都是 module_driver 宏展开成 module_init(__driver_init) + module_exit(__driver_exit)；编进内核（非 .ko）则走 builtin_driver/device_initcall、无 exit。THIS_MODULE 填到 drv->owner，提供 try_module_get/module_put 引用计数——设备绑定期间 .ko 不可卸载。

.ko 本身是可重定位 ELF（readelf -h 显示 Type: REL），.modinfo 段存 license/depends/alias/vermagic。加载流程：finit_module(2) 系统调用 → 校验 vermagic（KABI 版本魔串，不符即拒）→ 解析 __ksymtab（内核 EXPORT_SYMBOL/EXPORT_SYMBOL_GPL 导出的符号）→ 重定位 → 调 module_init。_GPL 后缀意为只对声明 GPL 兼容许可证的模块可见，是 KABI 的法律边界。drivers/base/ 里 driver_register/bus_register/platform_device_register 等都是 EXPORT_SYMBOL_GPL 的稳定（但 GPL-only）入口。

2.5 八大驱动子系统

每个子系统都遵循”核心层（定义 bus_type、匹配、统一 API、枚举算法）+ 控制器驱动（把抽象 op 接到具体 SoC 寄存器）+ 设备驱动（挂在总线上的具体外设）”三段式。最重要的分水岭是设备发现机制：

子系统 设备发现 自描述
PCI/PCIe 遍历 bus/dev/func 读 config space（vendor/device/class/BAR） 完全自描述
USB hub 检测端口 → 复位 → GET_DESCRIPTOR 读描述符 完全自描述
MMC/SD/SDIO 总线命令 CMD0/CMD8/ACMD41/CMD52 按 SDIO→SD→MMC 试探 半自描述（卡能应答 CID/CSD，控制器仍需 DT）
I2C 无枚举，地址靠板级声明 必须 DT/ACPI（地址 + compatible）
SPI 无地址无枚举，靠片选 + 板级声明 必须 DT/ACPI（reg=片选号）
GPIO gpiochip 是控制器，line 无自描述 必须 DT（gpio-controller + #gpio-cells）
clk 时钟树拓扑全靠 DT 必须 DT（clocks + #clock-cells）
dma-engine channel 靠 DT 申请 必须 DT（dmas + #dma-cells）
iommu 谁受哪个 iommu 管靠 DT 必须 DT/ACPI（iommus / IVRS / DMAR）

一句话：PCI 和 USB 是即插即用总线（硬件自带身份证），其余 SoC 片内总线全靠设备树描述拓扑——这正是 rv/aa SoC 必须带 DTB、而 x86 的 PCI 设备能裸枚举的根本原因。下面逐个拆。

PCI/PCIe。 一切的根是配置空间（每 function 256 字节，PCIe 扩到 4 KB），标准头含 Vendor/Device/Class/六个 BAR/Interrupt Line。核心层最经典的硬件 trick 是 BAR sizing（写全 1 回读）：对每个 BAR，先存原值、写全 1、回读（硬件把地址译码不关心的低位强制清零）、写回原值；回读值里最低那个”1”位的权重就是该 BAR 需要的窗口大小（size & ~(size-1) 取最低置位）。内核据此在物理地址空间分窗、再把分到的基址写回 BAR——这就是 PCI”自动分配地址”的实现。匹配是纯 ID（pci_match_id 比 vendor/device/subsystem/class），不需要 DT。中断走 MSI/MSI-X：设备不再拉 INTx 引脚，而是 DMA 写一个特定地址（CPU 的 LAPIC/IMSIC doorbell），数据即向量号；每 function 一张 MSI-X table、最多 2048 向量、各向量独立 address/data/mask，是 NVMe/网卡多队列 RSS 的基础。会用：pci_alloc_irq_vectors() 一个调用按掩码在 MSI-X→MSI→legacy 间自动回退。rv 上 MSI-X 的目标地址落到 IMSIC 的 interrupt file。

USB。 控制器（xHCI/EHCI/DWC3）实现 hc_driver，经 usb_add_hcd 注册并建立 root hub，之后所有外设都是 hub 端口下的子节点。枚举是教科书级自描述状态机：hub 检测端口 connect → hub_port_reset 拉复位并测速（USB2 设备复位中通过 chirp 协商高速）→ 从地址 0 升到唯一 devnum（SET_ADDRESS）→ 按速度定 ep0 包大小 → GET_DESCRIPTOR 读设备/配置/接口/端点描述符 → device_add 挂总线触发 interface 驱动匹配 → 建 /dev 节点供 libusb 用户态访问。数据传输的核心是 URB（USB Request Block）：usb_alloc_urb 分配、usb_fill_*_urb 填充、usb_submit_urb 提交（校验回调与设备状态、按端点类型分流、控制传输带 8 字节 setup 包、做 DMA 映射，交 HCD 的 enqueue），完成后 HCD 回调 urb->complete；message.c 提供 usb_control_msg/usb_bulk_msg 这种”提交 + 等完成”的同步包装。端点是设备内单向数据管道，分控制/批量/中断/同步四类。

I2C。 核心层匹配三路（DT 的 of_match_table → ACPI → i2c_device_id），但 I2C 总线无枚举能力——从设备地址扫不出类型，设备必须按 i2c_board_info（地址 + 名字）实例化，来源是 DT（reg=<0x50> + compatible）。收发核心是 __i2c_transfer：检查控制器实现了 master_xfer、仲裁丢失自动重试、原子上下文走 master_xfer_atomic；struct i2c_msg 数组承载多段（addr+flags+len+buf，I2C_M_RD 标读）。控制器驱动只需把 msgs 翻译成 START/地址/数据/STOP 时序。SMBus 是 I2C 子集协议，核心层可用 master_xfer 模拟。

SPI。 与 I2C 类似（DT/ACPI/id 三路匹配），但既无地址也无枚举——设备由片选线区分，DT 的 reg=<0> 即第几根 CS。传输单位是 spi_message（含一串 spi_transfer），spi_transfer_one_message 拉低片选后遍历每段调控制器 transfer_one，DMA map 失败可回退 PIO。spi_setup 配 CPOL/CPHA（时钟极性相位）、位宽、速率；SPI 全双工，tx_buf 与 rx_buf 同步移位。1.0 时代 embedded-hal 把”整线 SpiBus”与”带片选的 SpiDevice”分裂，正对应这里 controller 与 device 的关系。

MMC/SD/SDIO。 mmc_rescan（热插拔/上电入口，由工作队列触发）先验活已有卡或查物理在位，再按频率从高到低 mmc_rescan_try_freq 握手，探测顺序固定为 SDIO → SD → MMC：上电 → sdio_reset（CMD52）→ mmc_go_idle（CMD0）→ mmc_send_op_cond（CMD8/ACMD41 探电压）→ 依次试 mmc_attach_sdio/mmc_attach_sd/mmc_attach_mmc。顺序原因是 SDIO 卡对非法命令可能误响应，必须先用 CMD52/CMD5 筛出来；SD 用 ACMD41、MMC 用 CMD1，电气与命令集不同。卡能应答 CID/CSD/SCR 是”半自描述”，但控制器的寄存器基址/时钟/电源/检测引脚仍需 DT。SD/eMMC 经 block.c 暴露为 /dev/mmcblkN 块设备，SDIO function 则跑 WiFi/蓝牙模块驱动。

GPIO。 现代 GPIO 用不透明的 struct gpio_desc（取代旧的全局整数 GPIO 号）。控制器填 struct gpio_chip（get/set/direction_input/direction_output/to_irq）并 gpiochip_add_data 注册一个 bank。GPIO 必须 DT——哪根引脚是”reset””中断”纯靠 DT 的 *-gpios 属性 + #gpio-cells（通常 2：偏移 + flags），极性（ACTIVE_LOW）也编码在 flags 里。会用：消费者 gpiod_get(dev, "reset", flags) 经 DT 解析 reset-gpios = <&gpio1 5 GPIO_ACTIVE_LOW> 拿到描述符，gpiod_set_value() 自动按极性翻转、消费者只管逻辑值。/dev/gpiochipN 的字符设备 ABI v2 供用户态用。

clk（通用时钟框架）。 时钟硬件是有向树：晶振 → PLL → 分频器/选择器 → 门控 → 外设，CCF 用 struct clk_core 建模、每节点记 parent。基础原语是 clk-gate/clk-divider/clk-mux/clk-fixed-rate/clk-composite，控制器实例化这些节点、填 clk_ops（recalc_rate/set_rate/round_rate/enable/set_parent）注册为 DT clock provider。rate 传播：clk_set_rate 递归算最优分频/选源、可一路上溯到顶。prepare/enable 两段：clk_prepare（可睡眠，配 PLL 锁定等慢操作）+ clk_enable（原子，开门控）。clk 必须 DT——整棵树拓扑、consumer 用哪个时钟全靠 clocks = <&ccu CLK_FOO> + clock-names + provider 的 #clock-cells。会用：clk_get + clk_prepare_enable + clk_set_rate。

dma-engine。 控制器填 struct dma_device、实现 device_prep_dma_*（生成描述符）/device_issue_pending/device_tx_status。外设驱动作为 client，dma_request_chan（按 DT 的 dmas=<&dma 0> + dma-names 找通道）拿通道做内存↔外设搬运。描述符流水：device_prep_dma_memcpy/slave_sg/cyclic 生成 dma_async_tx_descriptor → 设回调 + tx_submit 入队拿 cookie → device_issue_pending 启动硬件 → 完成回调，dma_run_dependencies 触发依赖链（async_tx 框架，用于 RAID）。dma 必须 DT——哪个外设接 DMA 控制器的哪条请求线是 SoC 内部硬连线，只能由 dmas/#dma-cells 描述。

iommu（横切层）。 它在设备 DMA 路径上插一层 MMU：设备发出 IOVA（IO 虚拟地址），iommu 硬件查页表翻译成物理地址，实现设备隔离 + 让 32 位设备访问高内存 + 虚拟机直通。domain 是一组共享同一地址空间的设备集合；iommu_attach_device 把设备绑到 domain（写设备的 stream table/context entry）；iommu_map 建 IOVA→PA 映射（填页表 + 刷硬件 TLB，失败回滚），unmap 强制对齐到 pgsize_bitmap 的最小页逐页拆。控制器（Intel VT-d / AMD-Vi / ARM SMMU / RISC-V IOMMU）实现 iommu_ops + iommu_domain_ops。iommu 必须 DT/固件表——哪个设备受哪个 iommu 管、用哪个 stream-id，靠 DT iommus=<&smmu 0x100> + #iommu-cells 或 ACPI 的 IVRS/DMAR/IORT。消费者是 DMA 子系统与 VFIO/iommufd（设备直通给虚拟机）。

这套结论与权威源一致：LDD3 与内核文档对 PCI 枚举和”写全 1 读 BAR 大小”的描述吻合实现；USB 2.0 规范的复位时序、ep0 包大小、标准描述符与 hub 实现一一对应；SD/SDIO 规范的 CMD0/CMD8/ACMD41/CMD52 握手解释了 SDIO→SD→MMC 顺序；设备树规范定义的 #gpio-cells/#clock-cells/#dma-cells/#iommu-cells 对应各子系统的 DT 解析。

2.6 Rust for Linux：把驱动正确性提到编译期

Rust for Linux 用一套 binding 把上面的 C 模型安全化。module_platform_driver! 宏对应 module_init/exit；platform::Adapter<T: Driver> 桥接 C 的 platform_driver；驱动只实现 Driver trait 的 probe(dev: &Device<Core>, id_info) -> impl PinInit<Self, Error>——驱动私有数据在原地构造，要么完整构造、要么 Err，把 C 里”分配 + 半初始化 + 失败回滚”的易错模式换成代数。

两处设计最值得学。其一，Registration 的 RAII 注销：Registration 在则驱动已注册，它 drop（模块卸载）就自动调 platform_driver_unregister——消灭了 C 里”init 注册了但 exit 忘了注销”的整类 bug；它还把一个 post_unbind_rust 回调写进 device_driver 的一个 Rust 专属字段，C 侧在 device_unbind_cleanup 里调用它，在 remove 与所有 devres 回调完成后 drop 驱动私有数据（C/Rust 协同的精确收尾）。其二，Device 的 type-state：Device<Ctx> 用零大小类型参数编码”设备此刻处于什么上下文”——Normal（默认只读）→ Core（在总线回调如 probe 作用域内）→ Bound（保证绑定到驱动的整个生命周期）。访问 MMIO/IRQ/DMA 资源的方法（io_request_*/irq_*）只存在于 impl Device<Bound>，于是”在没绑定的设备上 ioremap 或请求 IRQ”这种 C 里的运行时 bug，在 Rust 里编译期就被拒绝。type-state 把”设备状态机的合法操作集”提升成了类型约束。

2.7 跨操作系统的驱动兼容

驱动复用有五条路径，代价递增：① ABI 级（直接加载二进制驱动）——ReactOS 是 Windows NT 的洁净室重实现，重做 ntoskrnl/hal/IO 管理器，让 DriverEntry/IRP_MJ_*/IoCallDriver 等 NT 内核 ABI 等价，从而直接加载未修改的 Windows .sys，代价是必须逐字节复刻 NT 内核结构与未公开行为，但换来”第三方闭源驱动生态友好”（Windows .sys 二十五年向后兼容）；② source-level（重编驱动源 + 兼容头）——FreeBSD 的 LinuxKPI 在 sys/compat/linuxkpi/ 提供数百个 Linux 内核头的 FreeBSD 实现，不加载 .ko 而是把 Linux 驱动源码（DRM/amdgpu、iwlwifi）在 FreeBSD 上重编，关键桥接字段 device_t bsddev 把 Linux 驱动语义翻译到 FreeBSD newbus；illumos 的 SPL 同理但方向相反（让 illumos 吸收 Linux 风格 API）；③ shim 桥接（运行时 thunk 翻译，如 ndiswrapper）；④ API 重写（照规范重实现，多数原生驱动）；⑤ VFIO/passthrough（用户态/VM 直通，需 IOMMU）。Fuchsia DFv2 是另一条路——把驱动跑在用户态 component、驱动间用 driver runtime + FIDL 通信，收益是失败隔离与不重启内核升级驱动；需注意其稳定 ABI 经 fuchsia.dev 官方核实是设计目标而非现状（”aims to provide a stable ABI … has not achieved ABI stability yet”）。

一条贯穿的张力是 ABI 稳定性：Linux 的 .ko 故意不稳定（KABI 随版本变，靠重编保证一致），换来内核演进自由；Windows .sys 稳定，换来闭源驱动生态。要兼容 Linux 驱动，最现实的是 source-level（LinuxKPI/DragonOS 路线）或 API 重写，而非 ABI 级——后者要复刻整套内核结构，成本极高。

3. 文件系统

文件系统是块设备之上、系统调用之下的一层，把”扇区的线性数组”抽象成”目录树 + 文件”。Linux 用 VFS（虚拟文件系统）把五十多种文件系统抽象成同一接口；本章先拆 VFS 这层骨架，再逐个拆六个具体文件系统的实现（寻址、分配、掉电一致性各不相同），最后看页缓存、日志、以及绕开 VFS 的两条路（FUSE 用户态、SPDK 用户态轮询）。

3.1 VFS 四大对象与操作向量

VFS 用”对象 + 函数指针向量”做面向对象多态：每个对象挂一组 *_operations，具体文件系统填表，VFS 通用代码只调 obj->op->method()。四大对象各管一摊：super_block（一个已挂载文件系统实例的全局元信息）、inode（一个文件的元数据与索引，与路径名无关）、dentry（路径树节点 + 名字到 inode 的缓存条目，即 dcache）、file（进程”打开文件”的句柄，含位置/标志/凭证）。关系是 file → dentry → inode → super_block，且 inode.i_mapping → address_space（页缓存）；一个 inode 可被多个 dentry 指向（硬链接），一个 dentry 被多个 file 打开。

四张操作表分别作用在不同层：file_operations（作用在打开的文件上：read_iter/write_iter/mmap/open/release/fsync/splice_*/copy_file_range/uring_cmd 等——现代文件系统只填 read_iter/write_iter，老式 read/write 留空走 new_sync_read）；inode_operations（作用在元数据/命名空间上：lookup 是 namei 的核心回调、create/link/unlink/mkdir/rename/getattr/setattr/listxattr/atomic_open/tmpfile，新内核这些都带 mnt_idmap * 做 idmapped mount 的 UID 映射）；super_operations（作用在整个实例上：alloc_inode/write_inode/evict_inode/sync_fs/statfs/freeze_fs/shrinker 回收）；address_space_operations（页缓存到磁盘的桥，已全部 folio 化：read_folio/readahead/writepages/dirty_folio/write_begin/write_end/direct_IO/bmap/migrate_folio/swap_*）。横向看，xv6 没有操作向量（只有硬编码的 readi/writei），FreeBSD 用 vop_vector，macOS XNU 用 vnop_*；Linux 拆成四张表是为了让”不变的 VFS 通用逻辑”与”可变的 per-FS 实现”彻底解耦——这是 Rust 内核（如 arceos 的 VfsOps/VfsNodeOps trait）也照搬的设计。

3.2 路径解析与 dcache 的 RCU 双模式

把 /a/b/c 解析成 inode 的过程叫 namei，主链是 open → path_openat → path_init（设起点）→ link_path_walk（逐分量走）→ walk_component → lookup_fast/lookup_slow → step_into → 处理挂载点与符号链接 → open_last_lookups → do_open → complete_walk。它最精妙的是两种并存模式，先 RCU-walk、失败再 REF-walk：

维度 RCU-walk REF-walk
并发控制 采样 d_seq seqlock + rcu_read_lock 防释放 引用计数 d_lockref + spinlock
取引用 不取（无原子写 cacheline） 每个 dentry/mount 都 lockref_get
速度 极快（无原子操作、无锁竞争） 慢（每分量一次原子增减）
适用 高频读、热路径全缓存命中 需睡眠（IO/权限）、automount、revalidate

RCU 查找 __d_lookup_rcu 在 hash 桶里 RCU 遍历、不取引用，靠 d_seq seqlock 做”hand-over-hand”校验（采样旧 dentry 的 seq、前进、再用 read_seqcount_retry 校验未变）。当 RCU-walk 撞上必须睡眠的操作（缺页 IO、权限要睡、网络文件系统的 d_revalidate）时，try_to_unlazy 对当前路径上每个指针补取引用并核对 seqlock 没变，成功就平滑转 REF-walk，失败返回 -ECHILD 让上层从头重走 REF-walk。负 dentry（d_inode == NULL）缓存”这个名字不存在”的事实，加速重复的失败 lookup（如编译器遍历 include 路径找头文件）。read/write 的 VFS 分派也值得记：vfs_read 先查 FMODE_READ/access_ok、rw_verify_area，再 file->f_op->read ?: new_sync_read（把同步读包成 kiocb + iov_iter 调 read_iter），成功后发 inotify 通知并记账。fd 表（fs/file.c）用 RCU 替换的 fdtable + bitmap 管理：alloc_fd 找空槽、fd_install 装入 struct file*、fget RCU 读并校验 f_count。

3.3 挂载、命名空间与挂载传播

一个 mount 是 (源 dentry, 挂载点, super_block) 三元组；d_mountpoint(dentry) 标记某 dentry 是挂载点，路径解析时 handle_mounts 跨越它。每个进程有自己的 mnt_ns（一棵独立的 mount 树），clone(CLONE_NEWNS) / unshare --mount 复制出新命名空间——容器正是靠 mount 命名空间 + pivot_root 把 rootfs 换成镜像层（详见 §12）。挂载传播（mount propagation）有四种类型：MS_SHARED（挂载/卸载事件在 peer group 双向传播）、MS_PRIVATE（不传播，容器常用以隔离）、MS_SLAVE（单向只收不发）、MS_UNBINDABLE（不可 bind，防递归 bind 爆炸）——systemd 把 / 设为 shared 引发的”mount 泄漏到容器”问题就出在这里。

3.4 页缓存：读、mmap 缺页、回写

页缓存是 address_space（即 inode->i_mapping）下的一棵 XArray（旧 radix tree），索引是文件页号、值是 folio（一个或多个连续 page 的头）。它是文件系统与内存子系统的接合点，三条路径要记牢：

  • buffered read：read → generic_file_read_iter → filemap_read → filemap_get_pages 按页号找 folio——命中直接 copy_to_user，未命中分配 folio 并调 a_ops->read_folio/readahead 触发磁盘 IO，正在 IO 则睡等 PG_locked/PG_uptodate。
  • buffered write 两段式：generic_perform_write 循环里先 balance_dirty_pages_ratelimited（写多了先回写，防脏页洪水），再 a_ops->write_begin（分配/读入目标 folio）→ copy_from_user → a_ops->write_end（标脏 + 解锁）。
  • mmap 缺页：mmap 装好 vm_ops 后，缺页中断走 filemap_fault 查页缓存（命中即建页表映射，未命中分配 + 读盘 + 睡等）；filemap_map_pages 一次缺页顺带把附近已缓存的 folio 批量建映射（fault-around，减少缺页次数）。

关键认知：read 与 mmap 共享同一页缓存，所以读过的文件再 mmap 是零拷贝命中。写则是”标脏 + 异步回写”：folio_mark_dirty 记账到 per-bdi 脏页计数，balance_dirty_pages 在脏页超 vm_dirty_ratio（默认 20%）时限速写者，per-bdi 的 flusher 内核线程 wb_workfn → wb_writeback → writeback_sb_inodes 周期性（默认 5 秒）或在 fsync/sync/内存压力下把脏 inode 的页提交成 bio。fsync 的核心就是 filemap_write_and_wait_range（发起回写并等完成）。一个反例分支是 DAX：对 NVDIMM/pmem，文件页直接映射设备物理内存、不进 DRAM 页缓存（无双重拷贝）。

3.5 jbd2 日志与三种数据模式

JBD2 是从 ext3 抽出的通用块设备日志层（ext4 与 ocfs2 共用），保证”一组块改动”原子落盘：先把改动顺序写进 journal 区（快），写完一个 commit block 标记事务完整，崩溃后 replay 有 commit 的事务即可恢复一致性、无需全盘 fsck。日志块有四类：descriptor block（描述后续数据块的最终落盘位置）、commit block（事务完整哨兵）、revoke block（阻止 replay 旧事务里已被覆盖的块，防把已删元数据写回）、superblock。事务状态机由 kjournald2 内核线程驱动（T_RUNNING → T_LOCKED → T_FLUSH → T_COMMIT → … → T_FINISHED），同一时刻只有一个 running 事务（其他句柄合并进它，叫复合事务），默认每 5 秒强制提交一次。

三种数据模式（mount -o data=）要分清，尤其 ordered 的保证常被说错：

模式 元数据 文件数据 崩溃后果 速度 默认
data=journal 进 journal 也进 journal 最安全，最新数据不丢 最慢（数据写两遍）
data=ordered 进 journal 写最终位置，但在元数据 commit 之前 元数据指向的总是已写的数据（不会读到旧块/垃圾） 中 是
data=writeback 进 journal 写最终位置，与元数据无顺序 元数据可能指向尚未写的数据块（读到旧内容/垃圾） 最快

ordered 的核心保证是”数据块先于引用它的元数据事务提交而落盘”，所以崩溃后不会出现”元数据说文件有这块、但块里是删除文件的旧内容”的安全漏洞；它不保证的是”最新写入的数据一定不丢”（那是 journal 模式才有）。要注意 metadata_csum（crc32c 元数据校验）与 journaling 是 ext4 中正交的两个独立 feature——这一点正是下文 ext4_rs 与 lwext4 的分水岭。ext4 还有 fast commit：ordered 模式下只记录最小增量（哪个 inode 的哪段变了），让 fsync 密集负载提速。

3.6 六个文件系统实现：寻址与掉电一致性

本地六个文件系统按难度递增，恰好把”寻址结构”与”掉电一致性”两条主线铺成谱。每个都先定义自己的块设备接口（FS 与硬件解耦的边界）——一个关键差异是只有 littlefs 在接口里强制暴露 erase，因为 NOR/NAND Flash 必须先擦后写、且擦的粒度远大于写，这一条决定了 littlefs 必须用写时复制（COW）而其余可以原地更新，是”硬件特性反向约束 FS 设计”的最干净案例。

easyfs（rCore 教学，约 980 行 Rust） 是最简骨架：磁盘分五区（超级块 / inode 位图 / inode 区 / data 位图 / data 区），DiskInode 含 28 个直接块 + 一级 + 二级间接块（封顶 8 MB 文件）。寻址 get_block_id 是间接块三段式（直接 / 一级 / 二级）。块缓存是全局 16 块的简易 LRU，get_ref<T> 用裸指针把块内偏移强转成 #[repr(C)] 结构体（零拷贝读结构体的核心 unsafe），Drop 时脏块自动回写。位图分配器是 first-fit（找第一个非全 1 的 u64、trailing_ones 定位第一个 0 位）。掉电一致性是无——block_cache_sync_all 全量刷盘、无日志无屏障，刷盘中掉电会留下位图已置位但 inode 未写的不一致。它的价值是约千行读懂一个完整可读写 FS。

ext2-rs（约 2550 行 Rust，只读） 还原 ext2 经典布局：磁盘切成多个 block group（每组自带位图 + inode 表减少寻道），超级块恒在字节偏移 1024、恒 1024 字节，用 assert_eq!(size_of::<Superblock>(), 1024) 等编译期断言锁死 on-disk ABI（很好的工程实践）。寻址是 12 直接 + 一/二/三级间接（比 easyfs 多三级），用位运算 index >> (log_block_size+2) 取索引（要求块大小是 2 的幂，比除模高效）。目录项是变长格式（inode | rec_len | name_len | file_type | name，按 rec_len 推进），区别于 easyfs 的定长 32 字节。它的写全 unimplemented!()——定位是读懂 ext2 布局而非生产读写。

ext4_rs（约 8160 行 Rust，生产级 ext4） 的核心是 extent 树取代间接块：extent 是”逻辑块段到物理块段的连续映射”而非”逐块指针”，大连续文件只需极少 extent。inode 的 60 字节 i_block 区域被复用成 extent 树根（transmute 成 Ext4ExtentHeader + 几个 extent）；find_extent 在内部节点二分找覆盖该逻辑块的 index 下钻、在叶节点算 物理块 = 逻辑块 - extent.first_block + extent 物理起点；写时 insert_extent/merge_extent（逻辑与物理都连续才合并以减少 extent 数）。一处必须核准的事实：ext4_rs 没有实现 JBD2 日志——超级块里的 journal 字段只是为正确解析 on-disk 格式而声明，全仓没有 transaction/commit/replay；它实现的是 crc32c 元数据校验（超级块、位图、block group descriptor、extent 尾、inode 各处校验和），属”检测损坏”而非”原子保证”。掉电只能靠 fsck + 校验和检测，不能原子恢复。它的分层（ext4_defs/ 纯 on-disk 结构 + ext4_impls/ 算法 + fuse_interface）值得大型 FS 借鉴。

fatfs（ChaN 的 FatFs，约 7250 行 C，FAT12/16/32/exFAT） 走完全不同的寻址哲学——FAT 是”簇链表”：一个数组以簇号为索引、值是”下一簇号”或链尾或空闲，文件就是一条簇链，”块映射表”集中放在卷头一张大表里而非每文件一棵树。代价是随机寻址 O(n)（必须从头跟链，FAT 最大软肋）。缓存只有一个单扇区窗口 win[]（极省 RAM，嵌入式友好）。掉电一致性靠两份完全相同的 FAT 表镜像：sync_window 写回主 FAT 后，若窗口在第一个 FAT 内就同步写 winsect + fsize（镜像 FAT 的对应扇区）——但这不是原子操作（两次写之间掉电会让两份不一致），只是”多一份拷贝供 fsck/chkdsk 参考”，是 1980 年代设计，远弱于 ext4 日志或 littlefs 的 COW。会用层面 fatfs 提供 f_open/f_read/f_write/f_mount 这套 POSIX-like API，移植只需填 diskio.c 的四个回调（disk_read/disk_write/disk_ioctl/disk_status），加之 UEFI 强制 ESP 用 FAT32、相机/U 盘通吃，是嵌入式与可移植场景的事实标准。

littlefs（约 6560 行 C，嵌入式掉电安全） 的两大支柱是元数据对 + CTZ 跳表，核心洞察是”元数据对提供原子更新但存储成本大、CTZ 跳表提供密集 COW 数据存储但更新成本大，两者组合——元数据对存指向 CTZ 跳表的引用”。元数据对是两块互为擦写备份的日志：每个元数据对 = 两个块地址，用 revision count 序列号比较哪块最新，块没满就直接 append 新 entry（旧 entry 不动，掉电仍有旧版本），一次 commit 可含多个 entry 共享一个 32 位 CRC（原子更新多个元数据），块满则 compact 到另一块。CTZ 跳表是 COW 文件数据结构，设计推演极精彩：正向 COW 链表 append 要连锁 COW 整条链（O(n) 写，废）→ 反向链表 append 只加新块（O(1) 写，但顺序读 O(n²)）→ CTZ 跳表在反向链表上加多级跳指针（块号 n 含 ctz(n)+1 个指针，读任意块 O(log n)、append 仍 O(1)、平均每块 2 个指针）。它在 FS 层做磨损均衡（revision count 反映擦写次数、分配时倾向少擦的块、坏块迁移——磁盘 FS 完全没有的层），块分配用滑动 lookahead 窗口免盘上分配表。掉电一致性是六者最强：元数据靠两块对 + revision + commit 级 CRC，文件数据靠纯 COW + 根引用原子切换，任意时刻掉电都能回到上一个有效 commit、且无需单独日志区。它的 DESIGN.md 从”链表 O(n²) 到反向链表到 CTZ 跳表”层层推演，是设计文档的范本。

lwext4_rust（约 3320 行 Rust + C 库） 是 lwext4（C 写的嵌入式 ext2/3/4）的 Rust 绑定——bindings.rs 是 bindgen 生成的 FFI、file.rs 全是 unsafe 调 C 的 ext4_fopen/ext4_fread，C 源经 CMake 编进来，no_std 环境用 ulibc.rs 的 #[linkage] 补 malloc/free/qsort 符号。与 ext4_rs 的关键对比：lwext4 有完整的真 JBD2 日志——ext4_journal.c（61 KB）有 revoke 记录的红黑树、commit header 的 crc32c、replay/recover，挂载序列是 ext4_device_register → ext4_mount → ext4_recover（重放日志）→ ext4_journal_start → 开 write-back 缓存。两个都叫”Rust ext4”，但 ext4_rs 从零写、没日志，lwext4_rust 绑 C 老库、有完整 JBD2——这是”绑成熟 C 库 vs 纯 Rust 重写”工程权衡的活教材（成熟的一致性机制极难从零写对）。

把六者并置成两张表：寻址上，间接块（easyfs/ext2）是逐块指针、extent（ext4/lwext4）是连续段映射、FAT 是集中式链表（随机慢）、CTZ 跳表（littlefs）是 COW 友好的对数跳转；掉电一致性上，easyfs 无、ext4_rs 仅校验和检测、fatfs 双副本非原子、lwext4 用 JBD2 日志、littlefs 用 COW + 双块对（后两者才真原子，磁盘选日志、Flash 选 COW）。这些独立 FS crate 存在的意义是可插拔后端——arceos 的 axfs 用 cargo feature（如 features=["fatfs"]）在编译期选具体 FS。

3.7 FUSE：把文件系统搬到用户态

FUSE 让用户态进程实现文件系统。一次 read(/mnt/fuse/file) 的旅程：内核 VFS → 内核 fuse 模块构造 fuse_in_header{opcode=FUSE_READ, nodeid, unique} 放进 /dev/fuse 请求队列 → 用户态守护进程 read(/dev/fuse) 收到 → libfuse 按 opcode 查 fuse_ll_ops[] 分派表调文件系统的 read 回调产生数据 → write(/dev/fuse) 回 fuse_out_header{unique, error} + 数据 → 内核按 unique 匹配请求、唤醒原 read、拷数据给用户。协议头里 nodeid 是目标文件的 inode 标识（低层 API 用 nodeid 而非路径），unique 用于匹配回复。opcode 共五十余个（FUSE_LOOKUP=1 是所有操作的前置——名字到 nodeid、GETATTR/OPEN/READ/WRITE/READDIR/INIT（握手协商版本能力）/CREATE/COPY_FILE_RANGE/SETUPMAPPING（virtiofs DAX 窗口）等）。挂载靠 open("/dev/fuse") 拿到 fd、再 mount(source, mnt, "fuse", flags, "fd=...,rootmode=...,user_id=...") 把 fd 交给内核，内核就把该挂载点的所有 VFS 请求路由到这个 fd 的队列——这是用户态守护进程能拦截文件操作的根（非特权用户走 fusermount3 setuid helper）。

会用 FUSE 有两套 API：低层（fuse_lowlevel_ops，回调拿 nodeid、显式 fuse_reply_*、异步）直接对接内核协议；高层（fuse_operations，回调拿路径字符串、返回即回复、同步）建在低层之上，自动维护 nodeid 与路径的映射。fuse-ext2 就是高层样例（getattr/read/write/readdir 回调拿路径，内部用 libext2fs 读 ext2 镜像）。现代 libfuse 3.x 还有 FUSE-over-io_uring（用 io_uring 环取代 read/write(/dev/fuse) 往返）、passthrough/backing（把某些 IO 直接转发到真实 backing fd，绕过用户态往返）、splice 零拷贝、多线程。性能权衡很清楚：每次 IO 至少两次用户/内核切换加一次进程调度，FUSE 比内核态 FS 慢（小 IO 尤甚），但崩溃不挂内核、可用任意语言写（sshfs/s3fs/gocryptfs/NTFS-3G 都是 FUSE）。

3.8 SPDK：用户态轮询，彻底绕开内核

走到另一极端是 SPDK 把整个 NVMe 设备从内核接管到用户态。做法是：往 sysfs 写把设备从内核 nvme 驱动解绑、改绑 vfio-pci（vfio 能编程 IOMMU 做内存安全，生产首选），把设备的 PCI BAR 经 mmap 映进进程地址空间、用户态直接 MMIO 按 NVMe 规范初始化控制器与队列对，最后用轮询取代中断。轮询完成的核心是相位位（phase tag）：完成队列（CQ）是环形缓冲、每条 completion 有一个 P 位、设备每写一圈翻转一次相位，驱动维护”期望相位”，cpl->status.p == phase 即”这条是本圈新写的”——纯读内存判断有无完成，零中断、零 MMIO。跨架构这里要插内存屏障（rv/la/ppc 用全屏障 spdk_mb、aa 用 dmb oshld load 屏障，x86 因 TSO 强内存序无需显式屏障——正是内存模型的活例）。全异步：IO 提交后立即返回，完成时由用户主动调 process_completions 触发回调，轮询线程独占 CPU 核（busy-poll，用 CPU 占用换吞吐与低延迟）。SPDK、FUSE、io_uring 三者本质都在”减少用户/内核往返”与”中断对轮询”之间做工程权衡——FUSE 把边界推向用户态守护进程、SPDK 让用户态完全接管设备、io_uring 在内核内做异步。

3.9 自己造文件系统的取舍

从这六个实现归纳，造一个 FS 的决策链是：先定块设备接口（最小 read_block/write_block 即可起步，目标是 Flash 就必须把 erase 放进接口，这决定 COW 还是原地更新）→ on-disk 结构用 #[repr(C)] + 编译期尺寸断言锁 ABI、读结构体优先 read_unaligned 而非裸指针 cast 避免对齐未定义行为 → 寻址从间接块起步、要性能上 extent 树、Flash 上用 CTZ 跳表 → 分配器位图 first-fit 最简、Flash 用 lookahead 窗口 → 块缓存嵌入式可用单扇区窗口、通用用 LRU + Drop 回写、写性能要 write-back → 掉电一致性是真正的分水岭：最低成本是 crc32c 校验（只检测不恢复），要原子则二选一——日志（写两遍，replay 恢复，磁盘选）或 COW + 双块对（新块加原子切根，无单独日志区，Flash 选）→ 目录定长项最简、大目录要 htree 哈希索引防 O(n) → 注意 FS 元数据锁与块缓存锁的层次以防死锁。一条务实结论是：成熟的一致性机制极难从零写对，绑成熟 C 库（lwext4 路线）常比纯重写（ext4_rs 缺日志）更可靠。

4. 网络栈

网络栈把”网卡收发字节”抽象成”可靠字节流（TCP）/数据报（UDP）/加密信道（TLS）”。本地四个栈恰好覆盖三条实现路线：smoltcp 与 lwip 是 L2–L4 的嵌入式协议栈、rustls 是 L6 的表示层（TLS）、dpdk 是绕过内核的用户态数据面。TCP/IP 分层与源码的映射是：应用（HTTP/DNS）→ TLS（rustls，夹在应用与 TCP 之间）→ L4 TCP/UDP（smoltcp 的 socket/tcp.rs、lwip 的 core/tcp*.c）→ L3 IP/ICMP/ARP → L2 Ethernet → L1 驱动（dpdk 的 PMD 在这层旁路内核）。

4.1 smoltcp：Rust 嵌入式 TCP/IP

smoltcp 是 no_std、可全静态分配（无堆）的协议栈，目录分 wire（无状态包编解码）、phy（设备抽象）、iface（收发调度）、socket（L4 状态机）、storage（环形缓冲）。

wire 层是无状态零拷贝访问器——每个协议一个文件，模式是”在借来的字节切片上直接读写、不拷贝”：字段偏移是 Range<usize> 常量，访问器直接在 &[u8] 上 NetworkEndian::read_u16(&data[field::SRC_PORT])（显式大端网络序），序号用有符号 i32（让回绕比较自然变成有符号环算术）。两套类型解耦”解析”与”语义”——Packet<&[u8]>（薄包装、惰性读字段、长度校验）+ Repr（已解析的高层结构，parse 验校验和、emit 写回），parse 失败返回 Error 而非 panic（裸机安全）。

phy 层的 token 模型是整库的核心，也是零拷贝的关键。 Device::receive 不返回数据，而返回一对令牌 (RxToken, TxToken)，真正收发延迟到令牌被 consume：RxToken::consume(|buf: &[u8]| …) 的闭包拿到原地的接收缓冲切片处理完即销毁令牌；TxToken::consume(len, |buf: &mut [u8]| …) 先向驱动要一块 len 字节的发送缓冲、闭包就地构造整个以太网帧、返回即发出——零堆分配、零拷贝。receive 之所以同时给一个 TxToken，是为了能基于收到的包原地构造回包（如 ICMP echo 回显）而不必为回包再分配。DeviceCapabilities 声明 MTU、突发大小、以及”网卡硬件是否已算 TCP/IP 校验和”（让软件跳过）。

iface 层是单线程 poll 事件循环：poll 把”从设备收”（socket_ingress：device.receive() 拿令牌对、闭包里解析帧分发到 IP/ARP、需要回包就用配对的 tx_token）与”往设备发”（socket_egress：遍历 socket 把待发数据经 device.transmit() 写出）编织在一起；发 IP 包前先做邻居发现（ARP/NDISC，未命中则发请求并暂存包）。设计哲学是没有内核线程、没有中断回调、没有锁——整个栈是”喂时间戳进去、吐出要发的包”的纯状态机、宿主决定何时 poll，这正是异步内核能直接嵌入它的原因。

TCP 状态机（单文件九千行）严格对应 RFC 793 的十一态（Closed/Listen/SynSent/SynReceived/Established/FinWait1/FinWait2/CloseWait/Closing/LastAck/TimeWait）。三次握手：主动开 connect 设 SynSent 态并发 SYN，收 SYN|ACK 校验 ack == local_seq_no + 1（否则 RST）转 Established；被动开 listen 收 SYN 转 SynReceived、收最终 ACK 转 Established。四次挥手由 close 按当前态决定（Established→FinWait1 发 FIN、CloseWait→LastAck），收 FIN 沿 Established→CloseWait、FinWait1→FinWait2/Closing/TimeWait、FinWait2→TimeWait 等转移。accepts() 是无副作用的”这个包归我吗”四元组前置判定，challenge_ack_reply 实现 RFC 5961 挑战 ACK 防盲注 RST。

它的超时重传（RTO）是 RFC 6298 的逐行实现（已与 RFC 核对完全一致）：首测 srtt = R; rttvar = R/2，后续 rttvar = (1-1/4)·rttvar + 1/4·|srtt-R'|（β=1/4）、srtt = (1-1/8)·srtt + 1/8·R'（α=1/8），RTO = SRTT + max(G, 4·RTTVAR) 夹到 [1s, 60s]，重传后 RTO 翻倍（指数退避）、连续退避三次后清测量（重新初始化），并用 Karn 算法在重传时丢弃当前采样（避免重传歧义污染 RTT）。快重传是”恰好第三个重复 ACK 触发”（不等 RTO，判定条件是载荷空 + ack 号重复 + 非窗口更新）。拥塞控制做成 Controller trait + AnyController enum（None/Reno/Cubic，可运行时切）——Reno 是慢启动指数增长（cwnd < ssthresh 时 cwnd += len）、拥塞避免线性增长、丢包时 ssthresh 减半；CUBIC（RFC 8312，BETA=0.7/C=0.4）用三次曲线 W(t) = C(t-K)³ + W_max，因 no_std 无 cbrt 而自实现 Newton-Raphson 立方根（裸机”自己造数学库”的典型）。发送窗口取 min(对端通告窗口, cwnd)。

4.2 lwip：C 嵌入式工业经典

lwip 与 smoltcp 同生态位但设计迥异。其零拷贝核心是 pbuf 链式缓冲 + 分层 header 预留：pbuf 分四类（PBUF_RAM 堆上 struct+payload 一次分配、PBUF_ROM 引用只读常量、PBUF_REF 引用外部易变内存、PBUF_POOL 来自固定池可链式分散聚集），而最精妙的是分层预留——pbuf_alloc(layer, len, type) 里 layer 枚举的数值就是要在 payload 前预留的字节数（PBUF_TRANSPORT 预留以太网 + IP + TCP 头空间），应用在传输层分配后，TCP/IP/Ethernet 各层往下走时用 pbuf_add_header 把 payload 指针向前移、原地写自己的头，全程不拷贝不重分配（与 smoltcp 的 token 就地构造、dpdk 的 mbuf headroom 同思想）。

lwip 区别于 smoltcp 的关键是三套 API（同一核心、三种打包）：Raw/callback API（tcp_new → tcp_bind/listen/connect → 注册 tcp_recv/tcp_sent/tcp_accept 回调 → tcp_write + tcp_output，无 OS、零拷贝、回调驱动、最高性能）；netconn API（顺序阻塞、跨线程经 mailbox 把每个调用打包成 api_msg 投给协议线程执行，避免应用线程直接碰协议核心）；socket API（在 netconn 之上做 BSD 兼容 + fd 表 + errno + 用户 buffer 到 pbuf 的全拷贝，最重但能直接跑 BSD socket 程序）。所有协议核心代码只在一个 tcpip_thread 里跑——这是 lwip 的并发模型：不是细粒度锁，而是把所有操作串到一个线程。可移植性的根是 sys_arch 移植层（sys.h 定义 OS 需提供的 sys_sem_t/sys_mbox_t/sys_mutex_t/sys_thread/sys_now，FreeRTOS/裸机/Linux 各写一份；NO_SYS=1 时这些是空宏、只能用 raw API），对应 smoltcp 把时间戳与 poll 交给宿主。网卡抽象是 struct netif 的三个函数指针：input（收到包向上递交）、output（IP 层调、做 ARP 后转 linkoutput）、linkoutput（真正把以太帧写进网卡）。TCP 实现的慢启动用 RFC 3465 的 ABC（按确认字节数而非 ACK 个数涨窗，抗 ACK division 攻击），RTO 用 Jacobson/Karels 的定点形式 (sa>>3)+sv（sa=8·SRTT、sv=4·RTTVAR，移位避浮点），快重传同样三个重复 ACK 触发，发送窗口同取流控与拥塞窗口的最小值。

4.3 rustls：typestate 握手机与 sans-IO TLS

rustls 是 L6 的 TLS 1.2/1.3 库，三处设计最值得学。其一，typestate 握手状态机——握手被建模成”一个状态消费输入、产出下一个状态”：客户端是 ClientState enum（ServerHello/Tls12/Tls13 等），每个状态是一个 struct ExpectXxx，其 handle 校验收到的握手消息、推进密钥日程、返回下一个状态（消费 self、move 成下一个类型）。非法状态转移在编译期就不可表达——拿着 ExpectServerHello 就只能处理 ServerHello，无法”在握手没完成时发应用数据”因为那条路径在类型上不存在（对照 smoltcp/lwip 的运行时 match state）。其二，CryptoProvider 可插拔密码学后端——它持 cipher suite 表、密钥交换组、安全随机源，两个官方后端是 rustls-ring（默认、纯 Rust+汇编、轻量）与 rustls-aws-lc-rs（FIPS 140-3 认证），换后端只改一行 with_crypto_provider，rustls 内核完全不依赖具体密码库。其三，证书校验用见证类型——ServerVerifier::verify_server_cert 返回 ServerCertVerified（零大小见证类型，只有校验器能造出来），逼迫调用方真的过校验才能拿到证明（typestate 思想用在校验结果上），默认实现 WebPkiServerVerifier 基于 webpki 与 RootCertStore。

最关键的是 sans-IO：rustls 不碰 socket，把 IO 切成”密文搬运 + 状态推进”两步——read_tls(rd) 把宿主从 TCP 读到的密文喂进内部缓冲（不解密不解析）、write_tls(wr) 把攒好的待发密文写给宿主 socket、process_new_packets() 才真正解密 + 喂状态机 + 产出明文，wants_read/wants_write 告诉宿主该读还是该写（配合 epoll/io_uring 做事件循环）。这让同一份 rustls 能跑在阻塞 std::net、tokio async、no_std 裸机、QUIC 之上——因为它对”怎么收发字节”零假设，与 smoltcp（宿主决定何时 poll）、lwip raw API（回调）是同一种控制反转哲学。会用 rustls 因此极简：网络栈只管把密文喂 read_tls、取 write_tls，TLS 逻辑零自研。

4.4 dpdk：用户态轮询数据面

dpdk 不是协议栈（没有 TCP），是包搬运地基——把网卡 DMA 队列直接映射到用户态、CPU 死循环轮询。收包入口 rte_eth_rx_burst 是强制内联的 static inline，核心是 p->rx_pkt_burst(qd, rx_pkts, nb_pkts) 这个函数指针——具体网卡的 PMD（Poll Mode Driver，在 drivers/net/）注册自己的向量化收包实现（AVX2/AVX512/NEON），一次调用从硬件 RX 描述符环搬一批 mbuf 指针，零系统调用、零中断（仅链路状态变化用中断），返回 0 就再轮、CPU 100% 忙等换极低延迟。标准骨架是 run-to-completion：同一个逻辑核 for(;;) 里收一批包、处理、发出，全程不跨核不入队不切线程，每个 RX 队列只被一个核轮询（无锁）。报文缓冲 rte_mbuf 是两段式零拷贝——data_off 是缓冲内的 headroom（默认 128 字节，预留头空间让各层 prepend 头不拷贝），mbuf 同时含元数据与指向数据、网卡 DMA 直接写进 mbuf 数据区、应用全程操作指针。内存地基是 rte_mempool（固定大小对象池，底层用无锁 ring）配每核本地缓存（避免每次分配都碰共享 ring 的原子操作）+ hugepage（2 MB/1 GB 大页替代 4 KB，大幅降 TLB miss、物理连续便于网卡 DMA）。整条路径是：网卡 → DMA 进 hugepage 里的 mbuf → PMD 轮询 RX 环 → rte_eth_rx_burst 返回 mbuf 指针批 → 应用处理 → tx_burst → 网卡 DMA 发出，内核完全旁路。

4.5 横向对比与会用

四栈并置：smoltcp（Rust、单线程 poll 无锁、token 借切片零拷贝、可全静态）、lwip（C、单线程 tcpip_thread 串行、pbuf 链 + layer 预留、三套 API）、rustls（Rust、sans-IO 宿主控 IO、typestate 协议安全）、dpdk（C、per-lcore 轮询无锁、mbuf DMA 直入、hugepage）。会用层面，建立一条 TCP 连接各家差异：smoltcp 是 SocketSet::add(tcp::Socket::new(rx,tx)) + socket.listen(port)/connect(cx, remote, local) + recv(|buf| …)（借切片）/send_slice(data)，事件靠宿主 iface.poll() 后查 socket；lwip socket API 是熟悉的 lwip_socket/lwip_bind/lwip_connect/lwip_recv（拷到用户 buf）/lwip_send，事件靠 select；lwip raw API 是 tcp_new/tcp_bind+tcp_listen/tcp_connect + tcp_recv 回调（给 pbuf）/tcp_write+tcp_output，事件靠回调；POSIX 内核 socket 则是 socket/bind/listen/connect/recv/send 配 epoll/io_uring（详见 §6）。三者都在”BSD socket 的全拷贝阻塞语义”与”零拷贝事件驱动”之间取不同点。

要自己造一个网络栈，从四栈提炼的路线是：设备抽象学 smoltcp 的 token 模型（Device::receive 返回令牌对、闭包就地收发、天然契合 no_std 与异步内核）；wire 层抄它的无状态访问器（Packet/Repr 双层、parse 返回 Result、序号用有符号环算术）；TCP 状态机直接移植它的十一态 match + RFC 6298 的 RttEstimator + Reno/Cubic 可切；并发模型先用单线程 poll（无锁最简）；TLS 直接挂 rustls（sans-IO 把密文喂进喂出即可，可换 ring 或国密后端）；高吞吐远期再看 dpdk 的 PMD 函数指针 + 每核 mempool + hugepage + run-to-completion；移植层借 lwip 的 sys_arch（定义宿主需提供的 sem/mbox/now 原语，一份接口多平台实现）；握手与校验用 typestate 把非法态在编译期消灭。一句话，传输层不必从零写——包一层 smoltcp 的胶水即可；TLS 不必自研——挂 rustls 即可；真要极致吞吐才上 dpdk 那套用户态数据面。

5. 系统调用机制与架构 ABI

系统调用是内核向用户态敞开的唯一合法接口（除 vDSO）。一次 write(1, "hi", 2) 从 C 到内核的全链是：libc 的 write → __syscall3(SYS_write, 1, buf, 2) 宏分发到架构内联汇编 → ecall/syscall/svc 陷入指令切到内核态 → 内核 sys_write() → 返回值（成功是字节数、失败是 -errno）回到 a0/rax/x0 → __syscall_ret 把 -errno 翻译成 errno + 返回 -1。三个不变量贯穿全章：陷入指令是唯一入口、寄存器约定钉死号与参数、错误用”负数返回”带内传递（errno 是 libc 在用户态二次加工出来的，内核不认识 errno 变量）。

5.1 系统调用不是函数调用：通用 trap 机制

普通函数调用（call/bl/jal）只改 PC，仍在同一特权级、同一地址空间、同一栈。系统调用必须跨特权级（U → S/内核），所以不能用 call，必须用专门的”自陷”指令。CPU 硬件执行该指令时原子完成一组动作（以 rv 为例）：保存返回点（sepc ← pc，返回时 +4 跳过 ecall）、保存状态（sstatus.SPP 记录原模式与中断使能）、记录原因（scause ← 8 表示 U 态 ecall）、跳转（pc ← stvec 内核预设的陷入向量）、切特权（进入 S 态）。关键点是通用寄存器不自动保存（与 x86 中断门压栈不同）——内核陷入入口第一件事就是把用户寄存器存进 trapframe、结束时再恢复，这也是为什么 ABI 必须钉死”哪个寄存器放什么”。

观察：现代 RISC（rv/aa/la64）高度趋同——号放高位的参数寄存器（a7/x8/a7）、参数 a0–a5、返回复用 a0，这是”自顶向下重新设计”无历史包袱的红利。三处怪癖必须懂：

  • x86-64 第四参数用 r10 而非 rcx——因为 syscall 指令的硬件行为是 rcx ← rip（返回地址）、r11 ← rflags，rcx/r11 被 CPU 占用无法传参，故把 System V 函数约定里的第四参数 rcx 改用 r10，clobber 列表显式列 rcx/r11。内核侧由 MSR 配置入口（LSTAR 是入口地址、STAR 是段选择子、FMASK 是进核时清哪些 rflags 位），返回用 sysret。它的历史前身是 i386 的 int 0x80（软中断，慢）与 Intel 的 sysenter（语义繁琐），64 位模式统一用 AMD 的 syscall。
  • i386 的寄存器荒：号 eax、参数 ebx/ecx/edx/esi/edi/ebp 六个全用满，但 ebx 同时是 PIC 的 GOT 基址寄存器，所以 PIC 下要用 xchg ebx, edx 在调用前后腾挪、五六参数甚至 push/pop ebp 走栈——这是 32 位寄存器荒加 PIC 冲突的历史包袱。它还把”本机最优 syscall 指令”的指针放在 TLS 偏移 16 处（call *gs:16），老 CPU 用 int80、新 CPU 用 sysenter，运行时择优——vDSO 救”指令发现”的经典用法。
  • MIPS 与 ppc 不用负返回：MIPS o32 用单独的标志寄存器 a3（a3 ≠ 0 表示出错、此时 v0 是正 errno），ppc 用 condition register 的 CR0.SO 位（出错时置位）——musl 在内联汇编里手动把它们归一成统一的”负返回”内部约定（MIPS 是 a3 && v0>0 ? -v0 : v0、ppc 是 bns+; neg）。

会用层面，发起一个原始系统调用就是用 syscall(SYS_xxx, args...) 或 musl 的 __syscall(...)；ARM 的 Thumb 模式因 r7 是帧指针还要临时换出再换回，32 位上 64 位参数（如 off_t）要拆成两个寄存器并按奇偶对齐——这些都是 libc 包装层替你处理的细节。

5.3 musl 的 syscall 宏体系

musl 的分发链很巧：用户写 __syscall(SYS_write, 1, buf, 2)，宏 __SYSCALL_NARGS 数出三个参数 → __SYSCALL_DISP 拼成 __syscall3 → 落到架构的内联汇编；__scc 把所有实参统一强转 long（规避指针/整型混传告警）。两个出口要分清：__syscall(...) 返回原始值（含 -errno，内部用），syscall(...) 经 __syscall_ret 设 errno（给应用用）。阻塞类调用（read/write/wait）还有可取消版 __syscall_cp（包一层检查 pthread_cancel 取消标志的逻辑）。老架构（i386/arm 老内核）没有独立的 socket 系统调用、统一走 SYS_socketcall 多路复用，新架构（rv/aa）才有独立号——musl 用 __alt_socketcall 先试独立号、得 -ENOSYS 再退回 socketcall。各架构的内联汇编风格不一：rv 是宏体直接 return、aa/arm 用 do{}while(0) 包裹防语句问题、x86_64/mips/la/ppc 因约束逐个不同而每个 __syscallN 独立写完整汇编。

5.4 errno：libc 造出来的带内信令

这是常被误解的一点：errno 不是内核概念，是 libc 造的。内核不设全局 errno 变量，而把错误编码进返回值——返回 0 或正数是成功，返回 [-4095, -1] 是出错、取反即 errno（4095 是内核的 MAX_ERRNO）。把它翻译成 POSIX 的 errno + 返回 -1 契约的唯一收口点是 __syscall_ret：

-4096UL 这个哨兵很精妙：合法返回值最大是 mmap 返回的高地址指针（无符号下也小于 -4096UL = 0xFFFFF000），而 [-4095, -1] 这 4095 个值划给 errno，用一个无符号比较就同时区分”合法大值”与”错误小负值”、零分支开销。errno 还是线程局部的——errno 宏实际是 (*__errno_location())，而 __errno_location 返回当前线程 pthread 结构里的 errno_val（经线程指针寄存器 rv 的 tp / x86_64 的 fs base / aa 的 TPIDR_EL0 取当前线程控制块），所以多线程并发系统调用不会互相覆盖 errno。完整的流是：内核 return -EINVAL(-22) → a0 = -22 → __syscall3 原样带回 → syscall() 经 __syscall_ret，因 -22 > -4096UL 成立故 errno = 22, return -1 → 应用 perror 打印 “Invalid argument”。

5.5 vDSO：不进内核的”系统调用”

vDSO（virtual Dynamic Shared Object）是内核映射进每个进程地址空间的一小段只读代码加数据页。某些”只读不敏感”的系统调用（取时间、取 CPU 号）若每次都陷入内核，特权切换加 TLB/流水线的开销远大于实际工作量——vDSO 让这些调用在用户态直接读内核维护的共享数据页返回，省去陷入。走 vDSO 的主要是 clock_gettime/gettimeofday/getcpu，各架构何时获得 vDSO 时间支持不同（x86 最早、rv64 较晚、la64 最晚）。musl 找 vDSO 的方式本质是在用户态手写一个迷你动态链接器：从 auxv 的 AT_SYSINFO_EHDR 拿到 vDSO 的 ELF header 基址（内核启动时经 auxv 传入），解析 program header 求装载基址、解析 PT_DYNAMIC 拿符号表与版本表、按名字加版本匹配 __vdso_clock_gettime 的地址；之后 clock_gettime 包装优先调这个函数指针、失败才退回真系统调用。性能差一个量级（vDSO 的 clock_gettime 约几纳秒、真系统调用约数百纳秒）。不是所有调用都能走 vDSO——要求无副作用、不改内核状态、数据可安全只读暴露。

5.6 ABI 稳定性五铁律

Linux 的 raw syscall ABI 永久稳定，是它与 Windows/macOS 的根本分野（详见 §11）：内核保证你 1990 年代直接 int 0x80 的静态二进制今天仍能跑。代价是号空间只增不减、字段只追加。五条铁律：① 系统调用号永不复用（老二进制硬编码号，复用等于老程序调到新功能，废弃的号只留空墓碑绝不回收）；② 寄存器约定永不变（a7/x8/rax 放号是契约，改了所有现存二进制全崩，新增只能新开号）；③ 结构体只在末尾加字段、永不删/不改序（如 stat → statx：不改老结构、新需求开新调用 + 新结构）；④ errno 列表只追加（已分配值含义永不变，范围锁死 1..4095）；⑤ 要破约定只能换新号（语义需变如 64 位 time_t，就开 clock_gettime → clock_gettime64、fstat → statx，老号冻结语义不动）。这五条正是 §6 里”系统调用只增不减、到 2026 已有四百余号”的原因。

6. Linux 系统调用全谱与专有高级接口

这一章把 Linux 的全部系统调用逐个列出（功能、关键标志、内核实现、POSIX 还是 Linux 专有），再深挖几组 Linux 专有的高级接口（io_uring/epoll/futex/eventfd/inotify/seccomp/eBPF/splice）。编号以 asm-generic/unistd.h 为准——这是 rv64、aa64、la64 三个现代架构共享的一张表（x86_64 因历史另有一张老表，号完全不同，本章并列对照）。

读表前先懂三件事。其一，编号宏：内核源用 __SC_3264(nr, sys_x32, sys_x64) 让 32 位架构取 *32 旧 large-file 变体、64 位架构取第二个（所以 rv64 上 __NR3264_fstat 就是 sys_newfstat、__NR3264_lseek 就是 sys_lseek，没有 *64 后缀的混乱）；被 time32/time64 分裂宏包住的项（clock_/timer_/futex/nanosleep 等）在 64 位架构上一律绑 time64 实现（不受 2038 年问题之害）。其二，*at 是现代架构的”正房”：generic 表删除了一切隐式当前目录的老形式（没有裸 open/stat/mkdir/dup2/pipe/poll/select，只有 openat/fstatat/mkdirat/dup3/pipe2/ppoll/pselect6），老接口由 libc 展开成 AT_FDCWD 调用——这是自顶向下重新设计无历史包袱的体现，x86_64 则因兼容保留了那些低号裸接口。其三，归属轴：POSIX（IEEE 1003.1 标准，含 POSIX.1b 实时扩展 timer/clock/sched 与 POSIX.1-2008 的 *at 族）、Linux（私有，无 POSIX 等价或语义不同）、Unix 非 POSIX（BSD/SVr4 遗产但从未进 POSIX 核心，如 chroot/flock/ptrace/ioctl）。

6.4 Linux 专有高级接口深挖

这些是 Linux 区别于 POSIX 的高级 ABI，KuOS 要跑 nginx/Redis/tokio/systemd/容器运行时必须吃透。理解它们有一条主轴——就绪模型（readiness）对完成模型（completion）：同步阻塞的 read/write 是”现在就做、做不完我就睡”；就绪模型（select/poll/epoll + eventfd/timerfd/signalfd/inotify）是内核只回答”哪个 fd 现在不会阻塞、你再自己去 read/write”；完成模型（io_uring）是内核回答”做完了、结果在这”，把提交与完成拆成两个共享内存环、批量化、可零系统调用。Linux 高级 I/O 的演化本质就是从”问内核能不能做”走向”叫内核替我做完”。

io_uring（完成模型的集大成，5.1，2019）。 它的全部入口只有三个系统调用：io_uring_setup（建实例，内核分配 SQ 环/CQ 环/SQE 数组并回填偏移）、io_uring_enter（提交 SQE 并/或等待 CQE）、io_uring_register（预注册 fd/buffer 等长期资源）。建好后用三个固定 mmap 偏移把内核环映射进用户地址空间——SQ 环存的是索引数组（这层间接允许乱序复用 SQE 槽）、CQE 数组直接在 CQ 环内、SQE 数组在独立段（默认 64 字节，passthrough 用 128 字节）；生产者写 tail、消费者写 head，用 release/acquire 配对保证环数据对端可见。它有两个让”0 系统调用 I/O”成真的关键设计：其一是 SQPOLL（IORING_SETUP_SQPOLL）——内核起一个轮询线程不断读 SQ tail，应用只要写 SQE + 更新 tail（纯用户态内存写）就根本不调系统调用，只有轮询线程休眠后才需一次 io_uring_enter 唤醒；其二是 io_uring_register 预固定 buffer 与 fd——配 READ_FIXED/IOSQE_FIXED_FILE 免去每次 IO 的 get_user_pages 页固定与 fget/fput 引用计数。它的操作码覆盖文件 IO、网络（含 accept/connect/send/recv）、POLL_ADD（把 epoll 风格的就绪等待也塞进完成环——io_uring 能”吃掉”epoll）、文件管理（openat/statx/renameat）、零拷贝（splice/tee/provide_buffers），还有 SQE 链接语义（IOSQE_IO_LINK 顺序依赖、IO_DRAIN 等前面全完成）。CQE 的 user_data 原样回传以把完成对应回请求、res 是等价于对应系统调用返回值的结果（负为 -errno）。会用层面没人手写裸环——Jens Axboe 配套的 liburing 封装了 setup+mmap 与环操作的内存屏障（io_uring_prep_read/submit/wait_cqe），tokio-uring、Redis 都走它。它统一了”磁盘文件也能真异步”（POSIX aio 只对 O_DIRECT 有效、glibc aio 是线程池假异步），但攻击面极大——曾贡献相当比例的内核提权 CVE，ChromeOS/Android 一度默认禁用，需配 seccomp 与 IORING_REGISTER_RESTRICTIONS 限制。

epoll（就绪模型的标准答案）。 三个系统调用：epoll_create1 建实例、epoll_ctl（ADD/MOD/DEL）增删改监视、epoll_wait/pwait/pwait2 等事件。它对 select/poll 的两个杀手锏都在源码里看得清：其一，所有被监视 fd 以 epitem 挂在一棵红黑树（ep->rbr）上，fd 集合常驻内核、每次 wait 不重传（O(log N) 增删查）；其二，只有”当前已就绪”的 epitem 挂在一条就绪链表（ep->rdllist）上，ep_poll 只遍历这条短链（O(就绪数) 而非 O(总 fd 数)）。而 O(1) 事件分发的本质是回调——epoll_ctl(ADD) 时把一个 ep_poll_callback 挂到目标 fd 自己的等待队列上，当设备就绪（网卡收到数据→socket 可读）驱动 wake_up 等待队列就触发该回调、把 epitem 挂上就绪链并唤醒阻塞在 epoll_wait 的进程；不是 wait 时去轮询所有 fd，而是每个 fd 就绪时主动把自己挂上就绪链。边沿对水平触发的区别也在这里：水平触发（LT，默认）报给用户后仍把 epitem 留在就绪链（只要 fd 还可读每次都报），边沿触发（ET，EPOLLET）报一次后不重挂、只有下次回调再触发才再上链（用户必须一次读到 EAGAIN 否则漏事件）；EPOLLONESHOT 报一次后禁用（多线程 worker 分发防竞争）、EPOLLEXCLUSIVE 让监视同一 fd 的多个 epoll 只唤醒一个（根治 accept 惊群）。它的致命短板是对普通文件无意义（普通文件 poll 永远返回可读，但磁盘 read 仍会阻塞）——这正是 io_uring 出场的理由。

把内核事件塞进 fd 的四件套。 设计哲学是”一切皆文件描述符”——把计数器、定时器、信号、文件系统事件都变成可 read、可被 epoll/io_uring 监视的 fd，于是一个事件循环就能统一管理所有异步源。eventfd 是最轻量的内核计数器（write 加计数、read 取走并清零，EFD_SEMAPHORE 则每次减 1），内核子系统（KVM irqfd、io_uring 的 REGISTER_EVENTFD）也用它把完成通知投给用户态。timerfd 把高精度定时器变成 fd（read 返回到期次数，TFD_TIMER_CANCEL_ON_SET 可在墙钟被改时取消，用于系统时间跳变检测）。signalfd 把异步信号转成同步可 read 事件（避免信号处理函数的 async-signal-safe 地狱，前提是要 read 的信号先被 sigprocmask 阻塞）。inotify 监控文件系统事件（IN_CREATE/MODIFY/MOVED_FROM/MOVED_TO 等，cookie 把 rename 两端配对），但不递归、队列会溢出。fanotify 比 inotify 强两点：能监控整个挂载点/文件系统，且能做访问权限决策（FAN_OPEN_PERM 拦截后用户写回 FAN_ALLOW/FAN_DENY）——杀毒软件与 HIDS 的内核钩子。这些在 BSD 对应 kqueue 的 EVFILT_TIMER/EVFILT_SIGNAL/EVFILT_VNODE（kqueue 不需 fd 化），Linux 选了 fd 化路线。

futex（用户态快锁的内核慢路径）。 它是 NPTL/glibc 实现 pthread mutex/cond/rwlock/semaphore 与 Rust std::sync::Mutex 的唯一底层系统调用。核心是无竞争时完全在用户态——原子 CAS 改 futex word（一个 4 字节对齐的用户空间 u32）即可获/放锁、根本不进内核，只有 CAS 失败（有竞争）才 FUTEX_WAIT 下陷睡眠、解锁方 FUTEX_WAKE 才下陷叫醒。FUTEX_WAIT 是原子的 compare-and-block（检查 *uaddr==val 与挂入等待队列在内核里原子完成，避免”检查后挂队前”丢唤醒）。还有 FUTEX_REQUEUE（把等待者从一个 futex 批量搬到另一个，pthread condvar 的 signal/broadcast 防惊群关键）、PI 系列（优先级继承防优先级反转，用 rt_mutex 实现）、配套的 robust list（线程异常退出时内核自动释放其 robust futex 锁防死锁）。新的 futex_waitv（5.16）一次等多个 futex（游戏引擎、Proton 翻译 Windows WaitForMultipleObjects 的强需求）。它与 io_uring SQPOLL 一脉相承——快路径在用户态、慢路径才陷内核。

userfaultfd（把缺页处理交给用户态）。 userfaultfd 返回一个 fd，用 ioctl 在上面握手（UFFDIO_API）、登记 VMA（UFFDIO_REGISTER 的 MISSING/WP/MINOR 模式）、解决缺页（UFFDIO_COPY 填数据、ZEROPAGE 填零、CONTINUE 用已有页内容、WRITEPROTECT 改写保护）。机制是当被登记的 VMA 缺页，内核不自己分配页，而是构造一条 uffd_msg（含故障地址与原因）投到 uffd fd 的消息队列、把故障线程挂起，监控线程 read(uffd) 取出消息决定填什么页、填完唤醒故障线程重试。它用于 VM 热迁移的 post-copy（先启 VM、访问尚未传输的页时拦截再从源端拉）、CRIU 的惰性恢复、用户态 GC；uffd fd 本身可被 epoll 监视，把”缺页”也变成事件循环里的异步源。

seccomp-bpf（用 cBPF 过滤系统调用）。 seccomp 装一个 classic BPF 程序逐系统调用裁决，过滤器输入 seccomp_data（系统调用号、架构、指令指针、六个参数——只能看寄存器标量不能解引用指针，是 TOCTOU 安全考量，且必须先检架构防多 ABI 绕过）。裁决动作从严到松：KILL_PROCESS/KILL_THREAD/TRAP（发 SIGSYS）/ERRNO（直接返回指定 errno）/USER_NOTIF（转发给用户态监督者）/TRACE/LOG/ALLOW，跑完所有 filter 取最严的。非特权进程装 filter 必须先 prctl(PR_SET_NO_NEW_PRIVS, 1) 防 setuid 提权绕过。SECCOMP_USER_NOTIF 让监督进程拿到一个 fd 接收被拦的系统调用、替目标进程模拟执行（容器运行时允许容器调 mount 但由 runtime 代理执行的核心机制）。它是 Docker 默认 profile、浏览器渲染进程沙箱、systemd 服务隔离（SystemCallFilter=）的地基，也常用来封掉 io_uring 的攻击面。

eBPF（把可验证的程序注入内核）。 一个系统调用 bpf(cmd, attr, size) 管一切——BPF_PROG_LOAD 加载程序、BPF_MAP_CREATE/LOOKUP/UPDATE 操作 map。三大对象：map（内核、eBPF、用户态共享的键值存储，类型有 HASH/ARRAY/PERF_EVENT_ARRAY/RINGBUF 等）、program（类型有 SOCKET_FILTER/KPROBE/XDP（网卡驱动最早期收包，DDoS 防御/负载均衡）/TRACEPOINT/SCHED_CLS 等数十种）、verifier（验证器）——eBPF 的安全基石，静态证明程序会终止且执行安全（有界循环、内存访问越界检查、寄存器类型与取值范围追踪、栈深限制），通过后 JIT 编译成宿主机原生码逼近原生性能。它是”用户态把逻辑安全地下放到内核热路径”的终极形态，与 io_uring（把 I/O 上放到内核异步执行）正好是一对消除用户/内核边界开销的镜像；seccomp 是它的前身/特例，现代内核用同一个 bpf_prog 承载二者。

零拷贝管道族。 核心思想是数据在内核 page/pipe buffer 间搬、不经过用户态 buffer，省两次拷贝。sendfile（fd 到 fd 直传，nginx 静态文件服务的零拷贝替代，文件页直接喂网卡 DMA，内部其实走 splice）；splice（通用零拷贝，但必有一端是 pipe——管道是枢纽，文件到文件得经 file→pipe→file 两段，SPLICE_F_MOVE 移页引用而非拷数据）；tee（复制 pipe 内容，两端都是 pipe，像 shell tee 一路存盘一路转发）；vmsplice（用户内存页映射进 pipe，配 SPLICE_F_GIFT 可零拷贝赠予，但要警惕页所有权语义——曾是 Dirty Pipe CVE 的相关面）；copy_file_range（文件间拷贝，杀手锏是若两 fd 在同一文件系统且 FS 实现了 copy_file_range/remap_file_range，可服务端拷贝（NFS 不回传客户端）或 reflink（Btrfs/XFS 的 COW 共享 extent，秒拷大文件不占空间），否则回退到 splice 逐页）。零拷贝是完成模型的好搭档——io_uring 有 OP_SPLICE/OP_TEE 把零拷贝也异步化批量化。至此 §6 的系统调用全谱与高级接口讲完，接下来回到用户态——程序如何在这套接口之上跑起来。

7. C 运行时启动链

main 不是程序的真正入口。内核 execve 之后到 main 之间，有一段由 C 运行时（CRT）负责的初始化，把”裸的指令流”变成”能用 TLS、能用 errno、栈有保护、全局构造已跑”的执行环境。这一节用 musl 把这条链拆透，再对照 relibc 看用 Rust 重写它是什么样。

7.1 三个启动对象：crt1 / Scrt1 / rcrt1

链接器按可执行文件类型选三个启动对象之一：crt1.o（静态可执行或非 PIE 动态可执行）、Scrt1.o（PIE，位置无关可执行，现代默认）、rcrt1.o（静态 PIE，无 ld.so 但有 ASLR）。一个常被误解的点是 Scrt1 与 crt1 源码完全一样——Scrt1.c 整个文件就是 #include "crt1.c"，区别纯在编译期 -fPIC（使取 main/_init 的地址走 GOT 间接、从而位置无关），不是”Scrt1 多了什么逻辑”。rcrt1 则把 ld.so 的自举搬进 crt：静态 PIE 没有外部 ld.so，但作为 PIE 仍需把自身的相对重定位打一遍，rcrt1 复用 ldso/dlstart.c 的自重定位代码、再用一个极简 __dls2 直接转 __libc_start_main（跳过完整动态链接器，因为静态 PIE 没有外部依赖）——这是”既要 ASLR 又不要 ld.so 依赖”的折中。

7.2 二段式启动

musl 的启动链是 _start（汇编）→ _start_c → __libc_start_main → 两阶段 → main。

第 0 段是架构相关的 _start 汇编，以 rv 为例：设 gp（rv 的全局指针，小数据寻址基址，且取 gp 自身时要 .option norelax 包住——加载 gp 时还不能用 gp-relative relaxation 是个鸡生蛋）、mv a0, sp（a0 指向内核建好的初始栈 [argc, argv…, envp…, auxv…]）、lla a1, _DYNAMIC、andi sp, sp, -16（16 字节对齐栈，psABI 要求）、tail _start_c。它不保存任何寄存器（内核只保证 sp 有效，其余未定义），用尾调用因为不返回。

第 1 段 _start_c 只解栈：argc = p[0]、argv = p+1，调 __libc_start_main(main, argc, argv, _init, _fini, 0)。

第 2 段 __libc_start_main 做真正的初始化，分两步。__init_libc 是早期初始化：定位 auxv（在 envp 末尾 NULL 之后）并解进定长数组、取 AT_HWCAP/AT_PAGESZ/AT_SYSINFO_EHDR（vDSO 基址）、设 __progname、初始化 TLS、初始化栈保护、做 setuid 安检（若 ruid≠euid 或 AT_SECURE，检查 fd 0/1/2 是否被恶意关闭、若 POLLNVAL 就 open("/dev/null") 占位，防止”setuid 程序的 fd 1 被攻击者关掉后第一次 open 拿到 fd 1、后续 printf 把秘密写进攻击者的管道”）。然后经过一道屏障转入 stage2：跑 _init 与 .init_array（C++ 全局构造、__attribute__((constructor))），再 exit(main(argc, argv, envp))。退出是对称的：exit → atexit/.fini_array → __stdio_exit（flush 所有 FILE）→ _Exit → SYS_exit_group（退整个进程所有线程）。

TLS 初始化值得记：rv 的线程指针就是硬件 tp 寄存器（x4），__set_thread_area 极简到 mv tp, a0; ret——rv 设 TLS 不进内核（不像 x86 要 arch_prctl），直接写寄存器；rv 是 variant I 布局（TLS 在线程指针之上），DTV 项有 0x800 偏置。栈保护 canary 从 AT_RANDOM 取 16 字节，64 位下还把 canary 的第 2 字节塞一个 NUL——牺牲 8 bit 熵，让 strcpy/gets 这类遇 NUL 即停的字符串函数无法把 canary 完整泄漏或覆写，NUL 放第 2 字节（不放第 1 字节）是为了 off-by-one 溢出仍能被检测到。

7.3 用四把锁钉死初始化顺序

这是 musl 启动代码里最精微的设计：编译器的内联、寄存器提升、把取址当链接期常量折叠，都会破坏”先初始化 TLS/SSP/重定位、后跑用户代码”的强顺序。musl 不信任编译器对全局初始化顺序的直觉，用四把锁逐一封死。其一，__init_libc 强制 __noinline__ + 外部链接——若它被内联进 __libc_start_main，那个临时大栈帧（auxv 数组、poll fd 数组）会和 main 同处一帧、整个进程生命周期都占着这块栈；强制不内联让 init 帧用完即弹。其二，stage2 前一道零指令的 __asm__("" : "+r"(stage2) : : "memory")——__init_ssp/__init_tls 刚把 canary 与线程指针写好，若编译器把 stage2 里”读 canary”或”读 tp/errno”的指令提前到 __init_libc 之前会读到未初始化值；"memory" clobber 告诉编译器此处任意内存可能被读写、+r(stage2) 让 stage2 指针”经过”这条 asm，强制其副作用排在 __init_libc 之后。其三，ld.so 里用运行时符号查找当屏障——errno/tp 的读取被编译器标成 pure/const（可自由提升），直接 C 调用下一阶段可能把读 &errno 的指令提前到 TLS 建立之前，于是 musl 用 find_sym 查 __dls2b 的地址再间接调，编译器无法跨这个运行时不可知的地址重排。其四，自举期 GETFUNCSYM 的 volatile asm + 静态内存指针——取下一阶段函数地址若被编成 PC 相对/链接期常量则可能尚未被重定位，于是把地址存进一个已被相对重定位修正过的 static 指针、用 "+m" 的 volatile asm 强制从内存读，而非内联计算。这四把锁是”自举期不能依赖尚未完成的重定位/初始化”这一难题的经典解法。

7.4 编译器隐式调用的运行时例程

还有一层和 libc 一起链进每个程序、但不属于 libc 的代码：编译器遇到硬件没有的操作（64 位除法、软浮点、memcpy 整块拷贝、rv 无 M 扩展时的乘除）会发出对一组约定符号的调用。GCC 用 libgcc，Clang/Rust 用 compiler-rt（C/汇编）或 compiler-builtins（Rust 重写），三者 ABI 兼容（同名同语义，命名编码如 __udivdi3 = unsigned divide di(64) 第 3 形态）。memcpy/memset/memmove 是这层的核心——所以裸机 Rust 也必须提供这几个符号（core 的切片拷贝、Vec、格式化最终都落到它们）。当目标 CPU 有硬件除法（RV64GC 的 M 扩展）编译器直接发指令，只有 RV64I（无 M）或 128 位运算才落到 __udivdi3 的软件长除法、__mulxi3 的移位-相加乘法。

rv 这里有一个独有的代码尺寸优化值得专门记——millicode __riscv_save_N/__riscv_restore_N（-msave-restore）：与其在每个函数 prologue 内联”压栈保存 s0–s11、ra”、epilogue 内联”弹栈恢复”，不如调一段公共库例程，prologue 变成一条 call t0, __riscv_save_N、epilogue 变成 tail __riscv_restore_N。它有几个精巧处：用 t0 当链接寄存器（调 save 时返回地址放 t0 而非 ra——因为 save 正要保存 ra、不能覆盖它，save 末尾 jr t0 返回）；多入口加 fall-through 链（__riscv_save_4 直接落进 _3_2，按函数实际用了几个 callee-saved 寄存器选入口）；rv64 按 2 个一组、rv32 按 4 个一组以维持 16 字节栈对齐；必须静态内嵌进每个共享库（因为 save/restore 用 t0、而 PLT header 也会破坏 t0，不能走 PLT 间接）。收益是每个函数 prologue/epilogue 从约 N×4 字节缩到约 8 字节，嵌入式代码尺寸显著下降，代价是多两次跳转。Rust 的 compiler-builtins 是 compiler-rt 的 no_std Rust 移植（作为 Rust sysroot 的一部分分发），整数除法用了比朴素长除法更快的分策略算法（按位宽与硬件选 trifecta/binary_long/delegate/asymmetric），还给 ARM EABI 提供 __aeabi_uidiv 别名。

crti.o/crtn.o 在 musl 与 relibc 里都是空的——现代只用 .init_array/.fini_array，不靠老式 .init/.fini 段拼接，它们存在只为提供链接器期望的占位（relibc 还把”为什么空”写进了注释：”we don’t support _init/_fini functions, only init/fini arrays”）。errno 也在这里收口：内核返回 -errno，libc 的 __syscall_ret 把 > -4096UL 的返回值翻译成”设 errno + 返回 -1”（详见 §5.4），而 errno 本身是线程局部的（errno 宏即 (*__errno_location())，指向当前线程 pthread 结构里的 errno_val）。

7.5 relibc：用 Rust 重写这条链

relibc 是 Redox OS 的 Rust libc（同时支持 redox 与 linux），是”libc 用 Rust 重写”的直接参考。它每架构用 global_asm! 写 _start（rv 同样 mv a0, sp 传栈指针，但用 jalr ra 普通调用而非 tail，因为入口函数 -> ! 不返回；x86 版还多做 SSE/x87 控制字初始化），relibc_start_v1 是它的 __libc_start_main（标 #[inline(never)]，等价 musl 的 noinline 屏障）。它的初始化顺序里有一处和 musl 同源的焦虑——alloc_init() 设好 Rust 全局分配器（dlmalloc-rs）前注释写着”if any rust memory allocation happen before this step we are doomed”，与 musl”TLS/SSP 先于一切”是同一种对初始化顺序的极度谨慎。errno 用 #[thread_local] 的 Cell，错误码翻译用类型化的 Errno(c_int) + or_minus_one_errno（把 Result<T, Errno> 转成”成功值 / 设 errno 返回 -1”）——这是 musl __syscall_ret 幻数 -4096 判断的 Rust 类型安全版，更难漏设 errno。它的 crti/crtn 同样故意空着。这给远期”用 Rust/Zig 写 libc”指了路：启动链、错误码、TLS 都能用类型系统重新表达，而不必照搬 C 的幻数与隐式约定。

8. libc / stdlib 全谱

到这里栈已经搭好，可以谈那一层每个 C/Rust 程序都离不开、却又最容易被当成”理所当然”的东西——标准库。这一节把它彻底摊开：C 侧穷尽八个本地实现的头文件 × 函数 × 是否落 syscall 的三维全景，Rust 侧穷尽 core/alloc/std 三层的所有模块与落点。一条主线贯穿始终——libc 的本质是”ISO C 标准函数 + POSIX 扩展”的语义实现，是用户态与内核 ABI 之间的桥；同一个 printf，桥的此岸语义一致，彼岸落地路径却因实现而异。

几处值得专门记。newlib stub 模型是它”可移植到任意裸机”的核心——libc 与 OS 解耦靠约 17–30 个 _xxx 弱符号，换 OS 只换这层 stub（本地 libgloss/riscv/sys_*.c 真 ecall 与 semihost-sys_*.c 半主机两套填空实证）。baselibc 子集小到 include/ 仅 7 个头（assert/ctype/inttypes/stdio/stdlib/string + klibc），无 unistd/无 syscall/无 pthread/无 math/无 locale，给”连内核都没有”的场景。picolibc 的 tinystdio 用 __file + put/get 函数指针替代重型 FILE，printf 可配置浮点开关大幅减体积。relibc 每个 C 头对应一个 Rust 模块（src/header/<头名>/mod.rs，用 #[no_mangle] extern "C" 导出 C ABI），src/platform/ 抽象 Linux/Redox 双后端，内存用 dlmalloc-rs、数学用 openlibm——它证明了 libc 的 ABI 契约与实现语言无关。

musl 的 syscall 落地机制有清晰的 file:line 锚点链可供仿造：号定义在 arch/riscv64/bits/syscall.h.in（asm-generic 编号）；内联汇编在 arch/riscv64/syscall_arch.h（__syscall0..6 把号放 a7、参数放 a0–a5、ecall、返回 a0）；两种入口 __syscall(无取消点) 与 syscall_cp(POSIX 取消点)；错误翻译在 src/internal/syscall_ret.c；errno 存储在 src/errno/__errno_location.c。这套五段式是”自己写 libc 或自己写 OS 的 syscall 层”最干净的参照。

libcxx 与 utf8proc 不是 C libc，单独定位。libcxx 是 ISO C++ 标准库——C 兼容头（cstdio cstring cmath 等，把 C 名字塞进 std:: 命名空间，底层仍调真 C libc）、容器（vector list map unordered_map set deque array）、算法工具（algorithm numeric functional tuple optional variant memory）、字符串流（string string_view sstream iostream regex）、并发（thread mutex condition_variable future atomic）、数值（complex valarray random chrono type_traits），它完全借道下层 C libc 落 syscall（std::fstream→fopen→openat，std::thread→pthread→clone）。utf8proc 是单文件 Unicode 规范化/属性引擎（被 Julia/PostgreSQL 用），纯查表零 syscall，导出 utf8proc_iterate(UTF-8 编解码)/utf8proc_get_property/utf8proc_tolower/utf8proc_decompose+utf8proc_normalize_utf32(NFC/NFD/NFKC/NFKD 规范化)/utf8proc_grapheme_break(字素簇边界)——比 musl 的 wctype/wcwidth 多了 libc 不覆盖的高阶 Unicode 算法（规范化与字素簇分割）。

8.6 Rust 三层标准库：core / alloc / std

C 侧讲完，转到 Rust。Rust 标准库不是一块铁板，而是三层同心圆，每层多引入一组前提假设——这个分层恰恰映射”从裸机到完整 OS”的每一级，是 no_std 内核/固件开发的根本认知。

层 crate 前提（你必须提供什么） 不能做什么 典型场景
core core 无（只要有 CPU + 编译器） 不能堆分配、不能开线程、不能 I/O 裸机固件 / 内核 / no_std MCU
alloc alloc 一个 #[global_allocator](实现 GlobalAlloc) 不能 I/O、不能线程、不能 OS 服务 no_std + 堆的内核 / unikernel / bootloader
std std 一个完整宿主 OS(Linux/Windows/macOS/Redox/WASI) — 普通用户态程序

关键事实是 std 把 core 和 alloc 全量 re-export：std::option::Option 就是 core::option::Option，std::vec::Vec 就是 alloc::vec::Vec，std::boxed::Box 就是 alloc::boxed::Box。所以应用代码写 std::xxx 其实大半在用 core/alloc 的东西；std 自己新增的只有那一圈需要 OS 的模块。#![no_std] 的含义就是不链接 std、只链接永远可用的 core 加可选的 extern crate alloc，panic 处理与全局分配器必须自己提供——relibc 本身就是 #![no_std] + extern crate alloc 写的（它给别人提供 libc，但自己只敢用 core/alloc，因为它是 libc 本体、不能假设有 libc）。

core 是零依赖基石。它的铁律是不碰堆、不碰 OS，唯一的”硬件相关”是 sync::atomic 和 arch（CPU 指令级，不需要 OS）。顶层稳定模块全列：基础抽象 any(类型反射 TypeId/downcast)、borrow、clone、cmp(PartialEq/Ord/Ordering)、convert(From/Into/TryFrom/AsRef)、default、marker(Send/Sync/Sized/Copy/PhantomData)；值与内存 mem(size_of/align_of/swap/replace/take/transmute/MaybeUninit/ManuallyDrop/offset_of!)、ptr(裸指针 null/read/write/read_volatile/write_volatile 即 MMIO 用/copy_nonoverlapping/NonNull/provenance)、cell(内部可变 Cell/RefCell/UnsafeCell/OnceCell)、pin(Pin 把数据钉死，自引用/异步前提)；数据 option/result(错误处理与 ? 落点)、iter(可组合外部迭代，零成本抽象核心，Map/Filter/Zip/Chain/Enumerate 适配器)、slice/str/array/ascii/char、num(NonZero/Wrapping/Saturating/ParseIntError)、ops(可重载运算符 + Range + Deref + Fn/FnMut/FnOnce + ControlFlow)、hash、fmt(Debug/Display/Formatter/format_args!)；底层 arch(SIMD intrinsic + asm!/global_asm! + rv64/x86_64/aarch64 子模块)、hint(black_box/spin_loop/unreachable_unchecked)、ffi(c_void/CStr/c_char 等 C 类型)、error(1.81 起 Error 进 core)、panic(Location/PanicInfo)；异步 future(Future trait/poll_fn)、task(Context/Waker/Poll/ready!)；同步 sync(只有无 OS 的 atomic 子模块)、time(只有 Duration 无时钟)、net(1.77 起进 core 的地址类型 IpAddr/Ipv4Addr/SocketAddr，无 socket)。

core::sync::atomic 单列——它是”无 OS 也能用”的硬件级原语：11 个原子类型（AtomicBool/AtomicU8..U64/AtomicI8..I64/AtomicUsize/AtomicIsize/AtomicPtr）、5 个 Ordering（Relaxed/Acquire/Release/AcqRel/SeqCst，对应 RVWMO/ARM weak/x86 TSO 内存模型）、关键方法 load/store/swap/compare_exchange/fetch_add/fetch_sub/fetch_or、自由函数 fence(线程级屏障)/compiler_fence(仅编译器屏障)。平台注意：AtomicU64 在 32 位 PowerPC/MIPS 缺失、ARMv6-M 只有 load/store 无 CAS，靠 #[cfg(target_has_atomic="64")] 条件编译。relibc 自己实现的 Mutex/once 就是纯 AtomicU32 + futex 搭起来的——这说明 atomic 是硬件级（无 OS 可用），而 Mutex 那种”睡眠等待”才需要 OS（futex syscall）。

alloc 加一个全局分配器就解锁了所有堆容器，但仍然没有 OS（不知道线程、不知道文件）。稳定模块：alloc(分配 API：alloc/dealloc/realloc/Layout/GlobalAlloc trait/handle_alloc_error)、boxed(Box 最简堆分配/Box::leak/into_raw)、vec(Vec 最常用容器/vec!/with_capacity/drain/retain)、string(String UTF-8 可增长/push_str/ToString)、collections(非 hash 的有序容器 BTreeMap/BTreeSet/BinaryHeap 优先队列/VecDeque 环形双端/LinkedList)、rc(Rc 单线程引用计数/Weak/downgrade)、sync(线程安全计数 Arc/make_mut)、borrow(Cow 写时复制)、ffi(CString 拥有所有权)、fmt(format!)、slice/str/task(Wake trait)。Rc 与 Arc 的硬件落点之别很关键：Rc 用普通 Cell<usize> 计数（非原子、单线程、快），Arc 用 AtomicUsize 的 fetch_add(Relaxed)/fetch_sub(Release)+fence(Acquire) 计数（原子、跨线程）——选错要么慢、要么不安全。

std 是 hosted = core + alloc + OS 服务。它新增/扩展的那圈模块，每个都对应一组 syscall：

std 怎么落到内核，经过一条 2024-2025 重构后的三段式分层：用户代码 → std 公开模块(std::fs) → feature-first 抽象层(std::sys::fs，跨平台统一接口) → 平台包装(std::sys::pal::unix，FileDesc/cvt/open64) → libc crate(extern "C" 绑定) → glibc/musl/relibc → 内核 syscall。重构的铁律是”除 std::os 外，std 其余部分只依赖 sys::feature_name、不直接依赖 sys::pal“。std 到底链不链 libc 有两条路并存：默认经 libc（x86_64-unknown-linux-gnu 链 glibc、*-musl 链 musl，通过 libc crate 的 extern "C" 调用——不直 syscall 是因为 glibc 的 NSS/getaddrinfo/locale/malloc 有状态、绕过会破坏，且 libc 维护 errno/信号/TLS/pthread、ABI 稳定靠它兜）；少数直 syscall（个别热点或 libc 不提供的用 asm! 直发 svc/syscall/ecall，典型如早期 getrandom、部分 futex/clone）。Rust 程序的启动链是 _start(crt1.o，来自 libc) → __libc_start_main → rustc 生成的 C-ABI main shim → std::rt::lang_start(设栈溢出守护/线程 guard/sigpipe/记录 argc-argv) → lang_start_internal(catch_unwind 包裹) → 用户 fn main() → 返回值经 Termination::report → exit_group。

relibc 是这套架构的活体同构样本——它和 Rust std 都是”公开 API 层 → 平台抽象 trait → 各平台 syscall 实现”。它的 Pal trait（src/platform/pal/mod.rs）列出 access/brk/chdir/close/clock_gettime 等方法，正是 std sys::pal 的同名抽象；Linux 后端 Sys（src/platform/linux/mod.rs）用 syscall! 直发（不经 libc，因为它本身就是 libc），Redox 后端换成 redox_syscall——和 std 多后端机制一致；默认分配器是 dlmalloc-rs（Doug Lea malloc 的 Rust 移植，一把 Mutex<Dlmalloc> 保护），这是”用 Rust 重写 glibc malloc”的活样本；错误码把 syscall 返回 > -4096 视为 -errno 转 Err(Errno)（musl __syscall_ret 幻数判断的 Rust 类型安全版）；同步原语用 atomic+futex 实现 Mutex/RwLock/Once/Condvar/Barrier；启动 crt0 是手写 global_asm! 的 _start + relibc_crt0，与 std 的 _start → lang_start → main 三段式结构同构。核心洞察是：relibc 证明”用 Rust 重写 libc”工程上完全可行（Pal trait + 多后端 + dlmalloc + cbindgen），而 std 本身不是 libc 替代品（它在 Linux 上依赖 libc）；两者合起来展示两条路——std 是”Rust 应用 → libc → kernel”，relibc 是”C 应用 → Rust(libc) → kernel 直发”。

这三层映射到一个全栈 OS 的固件/内核/用户态恰好严丝合缝：M-mode 固件停在纯 core（不挂分配器、不碰 OS，只用 option/result/ptr::write_volatile 操作 MMIO、atomic 做 boot hart 抢占、fmt 串口打印）；带堆的 bootloader/unikernel 是 core+alloc（挂一个全局分配器，参考 dlmalloc-rs 思路，解锁 Vec/Box/BTreeMap 管理 FIT 镜像和页表）；用户态程序是 std（需要内核自己提供一个 std::sys::pal 后端，实现 Pal 同款 trait 落到自家 syscall——relibc 的 Linux/Redox 双后端切换已示范了怎么加新后端）。这条”core→alloc→std 对应固件→引导→应用”的认知，是后面所有用 Rust 写系统级代码的总纲。

9. 动态链接运行时与 vDSO

§7 讲的是”静态视角的启动”——crt 把 main 跑起来。但绝大多数现代程序是动态链接的：它在跑 main 之前，先得让一个叫 ld.so 的程序把所有 .so 装进地址空间、把成千上万个符号引用填上真实地址。这一节把动态链接器拆开（仍以 musl ldso/dynlink.c 为主，relibc 作 Rust 三方对照），再讲 vDSO——那个”不进内核的 syscall”机制。

9.1 ld.so 自己也是 PIE：自举自重定位

动态可执行文件的 ELF 头里有个 PT_INTERP 段，写着解释器路径（如 /lib/ld-musl-riscv64.so.1）。内核 execve 时若发现它，就先把 ld.so mmap 到一个随机地址、跳它的入口 _dlstart，而不是直接跳主程序。这里有个先有鸡还是先有蛋的难题：ld.so 自己也是位置无关的（被装到随机地址），它必须先把自己的重定位打完，才能调任何全局函数——可”打重定位”这件事本身又是代码。musl 的 _dlstart_c 解法是只用纯局部、不依赖任何全局符号的代码完成自举：从栈解 argc/argv/auxv，算自身装载基址 base（优先 AT_BASE，否则用 &_DYNAMIC 与 program header 里 PT_DYNAMIC 的差），然后依次处理三种重定位表只打 RELATIVE 类（DT_REL 无 addend 是 *addr += base、DT_RELA 带 addend 是 *addr = base + addend、DT_RELR 见下），符号类的留给后面。这就是 §7 讲的屏障④（GETFUNCSYM 的 volatile 内存指针）要解决的场景——取下一阶段函数地址不能依赖尚未完成的重定位。

9.2 DT_RELR 压缩相对重定位

PIE 和共享库里绝大多数重定位是 R_*_RELATIVE（语义就是”把这个槽 += 装载基址”），每条 Elf64_Rela 占 24 字节几乎全是冗余。DT_RELR 用位图压缩，通常只占原 RELATIVE 表约 3% 空间，整个 PIE 虚拟内存能省 5%–10%。Android 2017 提出，2021-2022 进 glibc，musl 早期即支持，现代链接器 -z pack-relative-relocs 默认开。编码很巧：一串机器字交替两类项——地址项（最低位 0）是一个偶地址，直接对它重定位并把游标置于其后；位图项（最低位 1）的高 63 位（rv64）是位图，bit i 为 1 表示”游标 + i 字”处也要重定位，一个位图项覆盖 63 个连续字，可链式跟多个。这是个绝佳的三方对照教学样本——musl 在 ldso/dlstart.c（自举期）和 ldso/dynlink.c 的 do_relr_relocs（给依赖 .so 用，且开头 if (dso==&ldso) return 因为 ldso 自己的 RELR 已在自举做过）两处实现，relibc 在 src/ld_so/dso.rs 的 apply_relr 用 Rust 实现，三家逐行同构：

步骤 musl C（dlstart.c） relibc Rust（dso.rs apply_relr）
地址项（偶） relr_addr=base+rel[0]; *relr_addr++ += base addr=base.add(entry); *addr+=base; addr=addr.add(1)
位图项（奇） for(bitmap=rel[0]; bitmap>>=1; i++) if(bitmap&1) relr_addr[i]+=base while entry!=0 { if entry&1 {*addr.add(i)+=base} entry>>=1; i+=1 }
位图后前进 relr_addr += 8*sizeof(size_t)-1（=63） addr=addr.add(CHAR_BITS*size_of::<Relr>()-1)（=63）

权威核对：MaskRay 2024 博客、glibc BZ#27924、gabi ELF 草案的 SHT_RELR。相比 04-14 笔记早先完全没提它，这是动态链接里近年最值得补的一块。

9.3 通用重定位与重定位类型表

自举之后，ld.so 的 reloc_all 对每个已加载 dso 调 do_relocs，处理 DT_JMPREL(PLT)/DT_REL/DT_RELA/DT_RELR，最后对 RELRO 段 mprotect(PROT_READ)。do_relocs 的 switch(type) 把抽象重定位类型映射到具体架构的 R_RISCV_*：

REL_GOT/REL_PLT R_RISCV_JUMP_SLOT *addr = sym_val + addend GOT/PLT 槽（eager 填实址）

9.4 GOT / PLT 与”musl 不做惰性绑定”

这是 musl 与 glibc 一个重要的设计分野。glibc 默认惰性绑定（lazy binding）：函数第一次经 PLT 跳转时走 trampoline _dl_runtime_resolve 解析符号、回填 GOT，第二次起直接跳；优点是启动快（按需解析），缺点是 GOT 运行期可写、成了攻击面。musl 完全不做惰性绑定，一律 eager（启动时全解析）——do_relocs 对 REL_PLT/REL_GOT 直接当场填真实地址、没有 trampoline，整个代码库里没有 _dl_runtime_resolve 这种东西。权威是 musl wiki 的 functional-differences-from-glibc：不做惰性绑定既出于健壮性（惰性绑定失败无法报告错误），又因为它大幅减少了脆弱的、架构相关的代码。安全角度上这也更优：惰性绑定要求 GOT 可写、与 RELRO（重定位后把 GOT 设只读）冲突，而 musl 的 eager + full RELRO 天然防 GOT 改写攻击。所以”lazy 绑定是默认”这个常被当成普适事实的说法，其实只对 glibc 成立、对 musl 不成立——是个该按实现区分的点。

符号解析（find_sym）按依赖加载顺序广度优先在各 dso 符号表里查名字，用 DT_GNU_HASH（新，带 bloom filter 加速）或 DT_HASH（旧 SysV hash）定位。LD_PRELOAD 的 dso 插在链最前，故其符号优先命中——这正是 hook malloc/open 的原理。

9.5 TLS 的四种模型与 TLSDESC

线程局部存储的访问要按”编译期知道多少”分四档，越靠静态越快：LE（Local Exec，主程序自身 TLS，偏移编译期定，最快，R_RISCV_TLS_TPREL64）；IE（Initial Exec，启动即加载的 .so 的 TLS，tp + 固定偏移，要求 tls_id <= static_tls_cnt）；GD/LD（General/Local Dynamic，dlopen 来的 .so，运行时经 __tls_get_addr(tls_id, offset) 查 DTV）；TLSDESC（更快的动态 TLS，重定位时填一对 (resolver, arg)）。rv 的 TLSDESC resolver 汇编里有个和 §7 millicode 同思路的细节——__tlsdesc_static/__tlsdesc_dynamic 也用 t0 当返回寄存器（特殊调用约定，不破坏 ra），动态情形里查 DTV：dtv[modidx] + off - tp。rv 的线程指针是硬件 tp（x4），是 variant I 布局（TLS 在 tp 之上），DTV 项有 0x800 偏置。

9.6 三段式 __dls2 → __dls2b → __dls3

自举完成后，musl 的动态链接分三段推进，每段之间用 §7 讲的屏障③（运行时符号查找）隔开以防编译器跨阶段重排：__dls2 建 ldso 自身的 struct dso、decode_dyn、reloc_all(&ldso) 把 ldso 彻底重定位好，然后符号查 __dls2b；__dls2b 用内置 builtin_tls 建早期线程指针（__init_tp(__copy_tls(builtin_tls))），这样后续才能安全用 errno/TLS，再符号查 __dls3；__dls3 加载主程序 app 与 vdso 的 struct dso、递归 load_deps 解析所有依赖、reloc_all 全部、跑各 .so 的 .init_array，最后跳主程序 entry（AT_ENTRY）。relibc 的 src/ld_so/ 用 object crate 解析 ELF，Linker/Tcb 抽象齐全，apply_relr 与 musl 逐行同构，但仍标了很多 TODO，成熟度低于 musl。

9.7 vDSO：不进内核的 syscall

有些 syscall 频繁到”进内核一趟”的开销都嫌奢侈——典型是 clock_gettime。vDSO（virtual dynamic shared object）就是内核埋的一条近路，分三层。第一层，内核启动时构造一个微型 ELF（几 KB，含几条热 syscall 的纯用户态实现），每个进程被映射进地址空间、基址经 AT_SYSINFO_EHDR 放进 auxv（地址被 ASLR 随机化，cat /proc/self/maps | grep vdso 可见 [vdso] 段）。第二层，libc 的 __vdsosym 像迷你 ld.so 一样解析这个 ELF 的符号表（遍历 program header 算 base、解 dynamic section 拿 STRTAB/SYMTAB/GNU_HASH、按类型与绑定过滤 + 版本校验），首次调用解析后用原子 CAS 把函数指针缓存，之后所有调用直接 call 该指针、0 syscall；三层兜底是 vDSO → clock_gettime64 syscall → gettimeofday。第三层，vDSO 函数读一个内核每 tick 更新的共享数据页（cycle_last/mult/shift/mask），再读硬件计数器（rv64 csrr ..., time），算 (cycles - cycle_last) * mult >> shift 得 ns、加 boot 偏移、写 *ts——全程纯用户态读，无特权切换。各架构导出的符号略有不同：

架构 版本串 导出符号
rv LINUX_4.15 __vdso_rt_sigreturn/gettimeofday/clock_gettime/clock_getres/getcpu/flush_icache(rv 特有刷 I-cache)
x86-64 LINUX_2.6 __vdso_clock_gettime/getcpu/gettimeofday/time
aa LINUX_2.6.39 __kernel_rt_sigreturn/gettimeofday/clock_gettime/clock_getres（注意前缀是 __kernel_ 而非 __vdso_）

musl 的 arch/riscv64/syscall_arch.h 写死 VDSO_CGT_SYM="__vdso_clock_gettime"、VDSO_CGT_VER="LINUX_4.15"，与 man7 vdso(7) 完全一致。最后一个值得想清的问题：为什么不是所有 syscall 都走 vDSO？因为 vDSO 只能放纯读硬件状态、不改内核数据结构、不需特权的操作（时钟、CPU 号）；open/write/mmap/clone 都要改内核全局表（fd table/page table/task list），不可能在用户态完成。而 __vdso_rt_sigreturn 出现在表里不是性能优化，是信号返回 trampoline——它必须是一个内核已知的固定地址，让 handler 跑完能跳回来。

10. 编译器后端、工具链与 JIT

前面几节都在讲”二进制如何被装载、如何跑起来”。这一节回到更上游的问题：这个二进制是怎么被生产出来的。把编译器后端、整条工具链、以及”运行期才编译”的 JIT 摊开，最后落到一个全栈视角必问的问题——架构本身对 JIT 和动态翻译提供了什么硬件支持，rv 的 J 扩展在做什么。本地一手源是 libc/llvm-project（LLVM 23.0.0，2026-06-03 近 main 分支），rustc/GCC 无本地源处以官方文档/规范核对。

10.1 LLVM：narrow-waist 的库化基础设施

编译器纵向分层是”源码 → 前端 → 高层 IR → LLVM IR → 优化 → 后端 → MC → 机器码”。LLVM 的核心命题（Chris Lattner 2003）是把”目标无关的 IR + 模块化库”做成一条细腰（narrow-waist）：前端只管降到 LLVM IR、后端只管从 LLVM IR 出机器码、中间优化全复用。这与 GCC 的单体管线形成根本对立。库化是 LLVM 区别于 GCC 的根本——llvm/lib/ 下每个目录是一个可独立链接的库（IR/Analysis/Transforms/CodeGen/Target/MC/ExecutionEngine/LTO/…），这让 Clang、lldb、JIT、MLIR、外部语言都能按需取库，而不是 fork 整个编译器。

LLVM IR 是这条细腰的中枢，有三种等价形态：内存对象（Module/Function/BasicBlock/Instruction）、文本 .ll、二进制 bitcode .bc。本质是静态单赋值（SSA）+ 强类型 + 无限虚拟寄存器 + 显式 getelementptr/phi，Verifier.cpp 强制其合法性不变量，DataLayout 描述目标字长/对齐/端序使”目标无关 IR”仍能正确算 struct 布局。中端优化由 Pass + Pass Manager 组织，Transforms 分组：Scalar/(GVN/SCCP/DCE/SROA/LICM)、InstCombine/(peephole 代数化简)、IPO/(跨函数 Inliner/GlobalDCE/ThinLTO)、Vectorize/(LoopVectorize+SLPVectorize 自动向量化)、Utils/ 的 mem2reg（把 alloca 提升成 SSA 寄存器，是一切优化的前置）、Instrumentation/(ASan/TSan/PGO 插桩)、Coroutines/(C++20 协程 lowering)。

后端 CodeGen 有两条指令选择路径并存。SelectionDAG（默认成熟）把 IR BasicBlock 建成 DAG、合法化（i64 在 32 位机拆分等）、经 TableGen 生成的 ISel 表匹配成目标指令、调度、发射 MachineInstr；-O0 走 FastISel 牺牲质量换编译速度。GlobalISel（新，aa64 默认）四阶段流水线 IRTranslator→Legalizer→RegBankSelect→InstructionSelect，全局、可增量、更省内存。两路共用目标无关的寄存器分配（RegAllocGreedy/Basic/Fast/PBQP）、MachineScheduler、PrologEpilogInserter，最后 AsmPrinter 出 MC 层（含 DWARF/CodeView 调试信息）。MC 层完成汇编/反汇编/对象写出（ELF/MachO/COFF/Wasm 编码）。

后端清单里 rv 是观察”扩展爆炸如何被工程吸收”的最佳样本：每个 target 由 TableGen .td 描述文件 + C++ lowering 构成，rv 按扩展拆 .td——RISCVInstrInfoA.td(原子)/F/D/Q(浮点)/C(压缩)/M(乘除)/V+VPseudos(向量 RVV)/Zb*(位操作)/Zk*(密码)，以及厂商扩展 XTHead(平头哥)/XSpacemiT/XSf(SiFive)/XCV(CORE-V)/Xwch(沁恒)。这就是”为什么 LLVM 能跟上 rv 扩展爆炸”的答案——扩展即 .td，加一个扩展就加一组 .td 加少量 C++。LLVM 周边工具链组件也一并理清（很多是 GNU 工具的对位物）：

10.2 rustc 多后端：MIR 之前后端无关

Leo 点的”rustc 既支持 LLVM 也支持自建编译”这件事，根在 rustc 的管线设计。rustc 前半段到 MIR 为止完全后端无关：源码 → AST → HIR（去糖）→ 类型检查/借用检查 → MIR（rustc 自有的 CFG 化 IR，借用检查/drop 插入/常量传播都在这层）→ 单态化（泛型实例化）+ 划分 codegen units → 这里才分叉到具体后端。MIR 才是 rustc 真正的”自有 IR”，后端只负责”MIR → 目标机器码”那一段。

rustc 把”从 MIR 往下降”抽成一个后端无关的 crate rustc_codegen_ssa，定义一组 trait——BuilderMethods（编一个 basic block，定义 add/load/store/br/call 等 IR 构造）、CodegenMethods/CodegenCx（编一个 codegen unit 的上下文）、BackendTypes（关联类型把后端的 Value/BasicBlock/Type 抽象出来，LLVM 是 &Value、Cranelift 是 cranelift 的 Value，互不暴露）、CodegenBackend（驱动整个 crate 的 codegen）。数字证据是原来 27000 行的 rustc_codegen_llvm 被拆成 18500 行 LLVM 专属 + 12000 行后端无关 ssa，约 10000 行得以在三个后端间复用。三个后端：

后端 IR/引擎 状态(2026) 定位
rustc_codegen_llvm LLVM IR 默认 in-tree release 构建、全平台、最优代码质量
rustc_codegen_cranelift Cranelift IR (CLIF) 随 rustup 分发，2025h2 推 production-ready debug 构建快速编译，缩短 edit-compile-run
rustc_codegen_gcc GCC GIMPLE（经 libgccjit） in-tree 实验 覆盖 LLVM 不支持的架构（m68k/s390x/旧龙芯）+ GCC 工具链发行版

换后端是一次 dlopen——nightly 的 -Z codegen-backend=<path> 加载一个动态库、其中导出 __rustc_codegen_backend() 返回 codegen 对象，无需重编 rustc。为什么 rustc 既要 LLVM 又要自己的抽象，理由有四层：职责切分（类型/借用/单态化是 Rust 语义核心必须 rustc 自己做，机器码生成是通用工程、复用 LLVM 即可）；不被单一后端绑死（接 Cranelift 去 C++ 依赖、接 GCC 覆盖架构，是工程对冲）；编译体验（LLVM 优化重编译慢，Cranelift 给 debug 周期换速度，一个项目 debug 用 Cranelift、release 用 LLVM 最优）；Cranelift 自身也是独立的 codegen+JIT 库（Wasmtime 用它做 Wasm JIT），接它顺带验证了非 LLVM 后端可行。

10.3 GCC vs Clang vs LLVM：单体王朝 vs 模块化库

三者并列常被混谈，先消歧：GCC 是一整套自成体系、前中后端紧耦合的编译器套件；LLVM 是一套模块化的编译器基础设施库，本身不是一个编译器命令；Clang 是 LLVM 里的 C/C++/ObjC 前端 + 驱动，是”gcc 命令”的对位物。正确口径是拿 Clang ↔ gcc 比（都是前端/driver）、拿 LLVM ↔ GCC 内部架构比（都是基础设施）。

本质区别不在”有没有 IR”——GIMPLE 与 LLVM IR 地位等同（优化主战场的中层 SSA IR），RTL 与 MachineInstr 等同（贴机器做寄存器分配）——而在 IR 是否库化、是否对外开放。务实地看：GCC 强在成熟架构覆盖最广（含 LLVM 没有的冷门 ISA）、是 Linux 内核与多数发行版的事实标准、-fanalyzer 等；LLVM/Clang 强在模块化（催生了 rustc/swiftc/Julia/clangd/lldb/BOLT/MLIR 整个生态）、诊断精准（libclang/clangd 直接喂 LSP，IDE 生态由此而生）、JIT、跨语言复用、宽松协议利于商用魔改。二者长期互为进化压力共存——Clang 的精准诊断逼 GCC 改进诊断，GCC 的代码质量逼 LLVM 追平。

10.4 JIT：从 MCJIT 到 ORC v2，及各语言 JIT 全景

JIT（运行期按热度编译）和 LLVM 的关系，是理解”动态语言为何快”的钥匙。LLVM 的 JIT 演化是 Interpreter→legacy JIT→MCJIT→ORC v1→ORC v2：legacy JIT 自带指令编码器绕过 MC 层、每目标重复造编码逻辑被淘汰；MCJIT 复用 MC 层（IR 出标准 .o 对象再用 RuntimeDyld 装载重定位）但单体、不易 lazy/并发/远程；现役 ORC v2（LLVM 7 起）是模块化分层 JIT。ORC v2 的核心抽象：ExecutionSession（JIT 会话总线管符号查找/并发/生命周期）、JITDylib（模拟一个动态库的符号命名空间，addToLinkOrder 复刻静态/动态链接器的符号解析规则）、MaterializationUnit（按需产生符号定义，语言无关——LLVM IR 不被特殊对待，自定义编译器/直接写内存的 stub 走同一机制）、可叠加的 Layer（IRCompileLayer/IRTransformLayer/ObjectLinkingLayer/CompileOnDemandLayer 惰性按函数粒度）、两套 JIT-linking（新 JITLink 替代旧 RuntimeDyld）、现成的 LLJIT(即时) 与 LLLazyJIT(首次调用才编译)。最强的特性是 out-of-process/跨架构——通过 ExecutorProcessControl + RPC 把 JIT 出的代码送到另一进程甚至另一架构执行（lldb 表达式求值正是此用法）；符号查找是”三合一”（返回地址 + 触发编译 + 并发同步点）。ORC 的实战用户有 Julia、Cling(C++ REPL)、Swift 解释器、PostgreSQL 查询表达式 JIT。

10.5 架构对 JIT 与动态翻译的支持：rv J 扩展

JIT 的代码生成在所有架构上都能做，但”把刚写进内存的数据当指令执行”会撞上三个硬件现实，架构对 JIT 的”支持”就是对这三件事成本/便利的差异：I-cache/D-cache 一致性（刚写进 D-cache 的码，I-cache 还在取旧码）、流水线/预取队列陈旧、可执行内存安全（W^X 与指针标签隔离）。第一件事有一份最硬的横向对照证据——compiler-rt/lib/builtins/clear_cache.c（编译器为 JIT 代码自动调用的 __clear_cache）逐架构实现：

rv 的 J 扩展（Leo 特别点名，2026-06 仍未 ratify）就是为传统解释/JIT 语言、带大型运行时或语言级虚拟机而生的 umbrella task group。它点名要服务 C#/Go/Java/JavaScript/OCaml/PHP/Python/Ruby/Scala/WebAssembly 这些语言，针对它们共有的 GC、动态类型、动态分派、原始值装箱(boxing)、反射，并明确把动态二进制翻译/改写系统（DynamoRIO、QEMU、ftrace）纳入 scope，关注整数溢出检测、垃圾回收、指令 cache 管理、指令密度。设计姿态是”加速 JIT 序列的指令可选，软件运行时探测存在性再决定生成哪条码路径”。J 家族里最成熟的一块是指针掩码 Pointer Masking——让高位地址 bit 被硬件忽略，从而把标签塞进指针高位（tagged pointer/NaN-boxing/GC 颜色/内存标签），没有硬件掩码时每次解引用都要软件 mask、开销大，PM 让 boxing/内存标签/in-process 隔离近零开销。本地 LLVM 已定义全套子扩展（RISCVFeatures.td）：Ssnpm(S 级为更低特权提供 PM)、Smnpm(M 级)、Smmpm(M 级为 M-mode 自身)、Sspm/Supm(指示 S/U-mode 有 PM)。规范状态上 QEMU 已实现到 Zjpm v0.6.1，截至 2026 仍为 draft，社区诉求是为 RVA23 profile ratify 以便 HWASan 正式支持，Fuchsia 已出 RFC 探索用户态使用。它的近邻扩展常与 JIT/控制流安全一起出现——Zimop(May-Be-Operations 占位 op，给 landing-pad/tag 检查留编码空间)、Zicfilp(landing pad)+Zicfiss(影子栈)共同构成 CFI（保护 JIT 出码的间接跳转）。把三架构放一起作参照系：

11. 虚拟化与容器

讲完”二进制如何产生、如何跑起来”，接下来是”如何把它隔离起来跑”。隔离有两条根本不同的路：虚拟化（给每个负载一个独立内核）和容器（共享宿主内核、只框住视野与资源）。虚拟化的谱系——type 1 裸金属、type 2 宿主、type 1.5 混合、以及 microVM——本篇只做衔接性的速览，重心放在容器，因为容器恰恰是”不虚拟化”的隔离，把它拆透能反过来照亮虚拟化的边界。

11.1 虚拟化谱系速览

虚拟化按 hypervisor（VMM）的位置分三类。type 1（裸金属）直接跑在硬件上、自己就是个微内核管 VM（Xen、VMware ESXi、Hyper-V、rv 的 axvisor/bao）。type 2（宿主型）作为普通进程跑在通用 OS 上（VirtualBox、VMware Workstation、QEMU 用户态）。type 1.5（混合）是个有趣的中间态——一个通用内核加载一个内核模块让自己临时变成 hypervisor，Linux KVM 是典型：KVM 把 Linux 内核变成 type 1 的 VMM，但设备模拟、调度仍借宿主 Linux，所以既不纯裸金属也不纯宿主。硬件支持上，x86 靠 VT-x/AMD-V + EPT/NPT 二级地址翻译，aa64 靠 EL2 + Stage-2 翻译，rv 靠 H 扩展（hypervisor extension：HS-mode + 两级页表 hgatp + VS/VU 模式）。microVM（Firecracker、Cloud Hypervisor）是虚拟化里专为容器场景做的折中——拿掉 QEMU 全套设备模拟、只留 virtio-net/blk + serial，配 KVM 硬件虚拟化，既有 VM 的硬隔离边界又有接近容器的启动速度（约 125ms）和密度。这一段是为下面”容器为什么不是虚拟化”做参照系。

11.2 容器不是虚拟机：七件套

一句话定调：容器不是虚拟机——没有 guest kernel、没有虚拟 CPU/虚拟硬件、没有 hypervisor。一个容器进程就是宿主内核上的一个普通进程，只不过被内核的几项隔离/限额机制框住了视野与资源。把它拆开是七件套，全部是 Linux 内核既有特性，容器运行时（runc 等）只是把它们按一份 JSON（OCI config.json）组装起来：namespace（隔离”看到什么”）+ cgroup（限额”用多少”）+ rootfs（换根 pivot_root + overlayfs 分层）+ capabilities（裁剪 root 的特权位）+ seccomp（过滤可用 syscall）+ LSM（SELinux/AppArmor 强制访问控制）+ 默认 mount（/proc /sys /dev/pts）。其中 namespace 与 cgroup 正交——namespace 管视图、cgroup 管配额，互不替代。

最关键的是 user namespace 自 Linux 3.8 起创建不需要任何特权——它把容器内 UID 0（root）映射到宿主某个非特权 UID（如 100000），容器内”看似 root”逃逸到宿主只是普通用户，这是 rootless 容器（podman/lxc unprivileged）的内核基石。runc 把这点编码进顺序约束：它的 NamespaceTypes() 注释明确 user namespace 永远排第一不可移动（必须最先建立，后续 namespace 才能在新 userns 的权限下创建）。另两处语义值得记：PID namespace 只对子进程生效——调用 unshare(CLONE_NEWPID) 的进程本身不进新 PID namespace、它 fork 出的子进程才是新 namespace 的 PID 1（这是下面 nsexec 双 fork 的根因）；time namespace 只偏移单调/启动时钟、不偏移 CLOCK_REALTIME 墙钟（主要服务 CRIU checkpoint/restore 保持单调时钟连续）。

11.4 进出 namespace 的三把钥匙与 nsexec 双 fork

clone(2) 创建新进程并为它新建 namespace；setns(2) 让调用进程加入一个已存在 namespace（docker exec/nsenter 进运行中的容器、或 K8s Pod 复用 sandbox 的 netns 就走它）；unshare(2) 让调用进程自己脱离当前 namespace 进入新建的。runc 的策略是 setns 优先于 clone——只为要新建（config.json 里 path 空）的 namespace 出 clone flag，要 join 已有（path 非空）的走 setns。

runc 最精微的一段是 namespace 引导器 nsexec.c——它用 C 写、在 Go runtime 启动前作为构造函数执行。为什么必须用 C？因为 Go runtime 是多线程的，而 setns/unshare/clone 对线程和 userns 有严格时序要求，无法在 Go 的多线程调度下安全完成。它是个三阶段双 fork 状态机（stage-0 协调者 → stage-1 进 user 等 namespace → stage-2 进 PID namespace 的真正 init），双 fork 的两个根因恰是上面的语义：其一，user namespace 必须先建立，但 unshare(CLONE_NEWUSER) 会立刻丢掉旧 namespace 的全部 capability，导致父进程没法再写 uid_map（写它需要父在外层有 CAP_SETUID），所以策略是先 clone 出 stage-1、由仍有特权的 stage-0 替它写 /proc/<pid>/{setgroups,uid_map,gid_map}；其二，PID namespace 只对子进程生效，要再 fork 一层（stage-2）才能让某进程成为新 PID namespace 的 PID 1。引导完成后控制权交回 Go，Init() 接管一段安全敏感的序列：设 no_new_privs（防 execve 通过 setuid 提权，是非特权 seccomp 的前提）→ 设 SELinux 标签 → 装载 seccomp（若无 no_new_privs 则 seccomp 是特权操作、必须在丢 capabilities 之前装）→ finalizeNamespace 丢弃多余 capabilities + 切 user/group → 最后 execve 进用户程序，这就是”容器 PID 1”诞生的瞬间。换根用 pivot_root 而非 chroot（前者彻底卸掉旧根、防 chroot 逃逸）。

11.5 cgroup：限额”用多少”

cgroup 管资源配额，有 v1（legacy，每控制器一棵独立树）和 v2（unified，Linux 4.5+ 稳定，单一统一树）两代，差异显著：

维度 cgroup v1 cgroup v2
层级 每控制器独立树 单一统一树，进程唯一位置
控制器开关 编译期 + mount 绑定 运行时 echo "+cpu +memory" > cgroup.subtree_control
CPU 控制 cpu.shares + cpu.cfs_quota_us/period cpu.weight(1-10000) + cpu.max(quota period)
内存限 memory.limit_in_bytes(硬限) memory.max(硬) + memory.high(软带回压) + memory.low/min(保护)
设备控制 devices.allow/deny 白名单文件 eBPF BPF_PROG_TYPE_CGROUP_DEVICE 程序
PSI 压力 × √ cpu/memory/io.pressure
委派 × √ subtree_control 委派 + nsdelegate
内部进程约束 无 no-internal-process（有控制器的非根 cgroup 不能直接含进程）

runc 把 cgroup 管理抽成独立模块，v2 实现里每个控制器一个文件，本质是”把 OCI Resources 翻译成对 cgroupfs 文件的 write”——cpu.go 写 cpu.weight/cpu.max、memory.go 写 memory.max/memory.low、io.go 写 io.max 四类限速、pids.go 写 pids.max、psi.go 解析 some/full 压力数据；”把进程加入 cgroup”就是把 PID 写进 cgroup.procs 这一个文件。v1 与 v2 最大的实现差异是设备控制——v2 不再有 devices.allow/deny 文件，而是生成一个 eBPF 程序 attach 到 BPF_CGROUP_DEVICE（runc 这段注释明示移植自 crun 的 ebpf.c）。这也解释了为什么教学/比赛内核要”跑 Docker”必须实现 cgroupfs 三要素（控制器 + cgroupfs + 层级分组）——启动容器硬依赖 cgroup，内核无对应控制器 runc 就报 failed to write cpu.max。

11.6 capabilities + seccomp + LSM + rootfs

容器内的 root 不是全功能 root，而是被裁剪过 capability 集的 root。OCI 五集（effective 当前生效 / bounding 上界 / inheritable execve 跨越继承 / permitted 许可池 / ambient 环境）——runc 调 prctl(PR_CAPBSET_DROP) 逐个丢弃 bounding、capset() 设其余四集，Docker 默认保留约 14 个（CAP_CHOWN/CAP_NET_BIND_SERVICE/CAP_SETUID 等），丢弃 CAP_SYS_ADMIN/CAP_SYS_MODULE 这些危险位。seccomp 用 BPF 过滤可用 syscall——defaultAction（如 SCMP_ACT_ERRNO/SCMP_ACT_KILL_PROCESS/SCMP_ACT_ALLOW/SCMP_ACT_NOTIFY）加每条 syscalls[] 的 names/action/args（可按参数值匹配），架构常量已列到 SCMP_ARCH_RISCV64/SCMP_ARCH_LOONGARCH64（即 seccomp 已支持 rv/la），其中 SCMP_ACT_NOTIFY 是现代亮点——把被拦截的 syscall 经 UNIX socket（SCM_RIGHTS 传 seccompFd）转交用户态 agent 处理，rootless 容器靠它模拟 mount/mknod 等特权 syscall。LSM 层写 apparmorProfile/selinuxLabel；rootfs 是镜像层只读（lowerdir）叠加 + 容器可写层（upperdir）+ 合并视图（merged）的 overlayfs。把这些拼起来对照虚拟机，”不是虚拟化”的本质一目了然：

维度 容器 虚拟机
内核 共享宿主内核（无 guest kernel） 每 VM 独立 guest kernel
隔离机制 namespace+cgroup+caps+seccomp+LSM 软隔离 硬件辅助虚拟化 + 二级地址翻译
攻击面 整个宿主内核 syscall 接口（大） hypervisor + virtio 设备模型（小）
启动 毫秒级（就是 fork+exec） 秒级（要 boot 内核）
密度 单机数百到数千 单机数十
跨内核版本 × 必须兼容宿主内核 ABI √ guest 任意 OS

11.7 OCI 三规范

OCI（Open Container Initiative，2015，Linux 基金会）把 Docker 拆出的事实标准固化为三份独立规范。runtime-spec 定义”怎么把一堆文件跑成容器”——一个 filesystem bundle = config.json（配置）+ rootfs/（根目录），config.json 里 linux.namespaces[]（path 空=新建/非空=join）、uidMappings/gidMappings、linux.resources（cgroup 限额）、linux.seccomp、maskedPaths/readonlyPaths 等字段一一对应内核机制，生命周期是 creating→created→running→stopped 的 12 步状态机（穿插 prestart/poststart 等 hooks），runc CLI 的 create/start/run/exec/kill/delete/state/pause/checkpoint/restore 一一对应。image-spec 定义”镜像长什么样”——内容寻址（一切由 sha256 digest 指向，形成 Merkle DAG），媒体类型有 Image Index（多架构清单列表）/Image Manifest（单架构 config+layers）/Image Config（运行配置 + rootfs.diff_ids）/Layer（tar 或 tar+gzip/zstd），三个哈希概念要分清：DiffID 是单个未压缩 layer tar 的 sha256，ChainID 是层叠加后的复合递归哈希（区分顺序，ChainID(C) ≠ ChainID(A|B|C)），ImageID 是 config JSON 自身的 digest。distribution-spec 定义”registry 怎么传”——/v2/ 前缀的 HTTP API（end-1 到 end-14 共 14 个端点），拉镜像是先 GET manifest 再逐个 GET blob 按 digest 校验，推镜像反序（先传 blob 后传 manifest），跨 repo 用 mount 去重免重传，OCI 1.1 新增的 referrers API（end-12）把签名/SBOM/attestation 以 subject 弱关联挂到镜像上。

11.8 容器运行时全谱

运行时分两层：高层（管镜像/网络/存储/CRI/生命周期 API）和低层（按 config.json 真正建容器）。逐个看（本地 clone 实证）：

项目 语言 层 定位
runc Go + C 低层 OCI runtime-spec 参考实现，Docker 捐给 OCI，namespace 引导用 C nsexec.c
crun C 低层 Red Hat 的 C 实现，比 runc 更小更快，原生 cgroup v2 + eBPF
containerd Go 高层 工业标准 daemon，CNCF graduated，Runtime v2 shim 模型
CRI-O Go 高层 专为 K8s 的 CRI 运行时，无多余功能，用 conmon 监管
podman Go 高层 daemonless + rootless，Docker CLI 兼容，原生 pod
lxc C 低层 老牌系统容器(2008)，跑完整 init 的”轻量 VM”体验，首个支持 unprivileged

几处机制值得记。containerd 的 Runtime v2 shim 模型——它不直接管容器进程，而是为每个容器/Pod 启一个 shim 进程（containerd-shim-runc-v2），shim 调 runc 建容器并常驻持有容器 stdio + 收 exit code，这样 containerd daemon 重启不影响运行中的容器（CRI-O 的 conmon、podman 的 conmon 是同思路的小监管进程）。podman 的 rootless 靠 user namespace + newuidmap/newgidmap（subuid/subgid 映射）+ fuse-overlayfs（无特权 overlay）+ slirp4netns/pasta（无特权网络）。低层还有两类安全沙箱运行时——gVisor/runsc 用 Go 在用户态实现一个 Linux 内核（Sentry），拦截容器 syscall 在用户态模拟、容器不直接碰宿主内核；Kata Containers 每容器一个轻量 microVM（QEMU/Cloud Hypervisor），OCI 兼容但实为 VM——二者都实现 OCI runtime-spec，可被 containerd/CRI-O 当低层 runtime 直接替换 runc。再往上是 K8s 与容器层的三接口：CRI（kubelet ↔ containerd/CRI-O 的 gRPC）、CNI（插件式配 netns 网络 bridge/Calico/Cilium）、CSI（插件式挂存储卷）。

11.9 容器 vs 虚拟机 vs microVM 光谱

把隔离强度与性能放在一条光谱上收尾，从强隔离重量级到弱隔离轻量级是：传统 VM → microVM(Firecracker/Kata) → gVisor → 容器(runc)：

维度 容器(runc) microVM(Firecracker) gVisor(runsc) 传统 VM(QEMU/KVM)
内核 共享宿主 独立精简 guest 用户态 Sentry 完整独立 guest
隔离强度 弱（共享内核 ABI） 强（VT-x/RVH 二级翻译） 中（拦截 syscall） 强
攻击面 宿主全 syscall hypervisor+virtio（极小） Sentry+少量 host syscall hypervisor+全设备模型
启动 毫秒 约 125ms 亚秒 秒级
内存开销 近零 约 5MB/VM 中 数十到数百 MB
密度 数千/机 数千/机 数百 数十

microVM 是这条光谱上最巧的折中——拿掉 QEMU 的全套设备模拟、只留 virtio-net/blk + serial，配 KVM 硬件虚拟化，既有 VM 的硬隔离边界又有接近容器的启动速度与密度，Firecracker（AWS，Rust 写）正是 Lambda/Fargate 多租户后端，Kata 则把 microVM 套进 OCI/CRI 接口让 K8s 无感替换 runc。它和 unikernel 处在相近生态位（都追求轻量隔离 + 快启动），区别在 unikernel 是”每应用一个完整迷你 OS”而 microVM 是”跑通用 guest 的精简 VM”。源码层面这条光谱的分界很硬：runc 全程只调 clone/setns/unshare + 写 cgroupfs + pivot_root + seccomp/capset，没有任何硬件虚拟化指令——这从代码层面证明了”容器是被框住的普通进程”，而 microVM 才引入 KVM 硬件虚拟化。

12. 跨 OS：API 一览与跨 OS 运行

前面整篇都站在 Linux/POSIX 的视角。这一节做两件事：横向给 Windows 与 macOS 一张 2026 的 API 一览表（功能 + 与 Linux/GNU/POSIX 的对应），看清三家在”稳定边界”上的根本分野；再梨花带雨地讲一下跨 OS 运行——Linux 跑 Windows 程序（wine）、Windows 跑 Linux 程序（WSL）、以及承载它们的 Hyper-V 与 VMware。

12.1 三家的稳定边界：一个根本分野

理解 Windows 和 macOS，得先抓住一件事：它们与 Linux 在”哪一层是稳定 ABI”上选择截然不同。Linux 的稳定边界是 raw syscall 号（最底层）——内核保证一个 1990 年代直接 int 0x80 的静态二进制今天仍能跑，代价是号空间只增不减、字段只追加（语义要变就开新号，clock_gettime→clock_gettime64、fstat→statx，老号冻结）。Windows 和 macOS 反过来——它们的 syscall 号每个版本都可能变（不稳定），强制所有程序经各自的官方动态库（Windows 经 ntdll.dll，macOS 经 libSystem.dylib），不许静态链接绕过。这不是缺陷而是有意的设计选择：把稳定边界上移到 DLL/dylib，内核就能自由重构 syscall 表。三家一句话总纲：

维度 Linux Windows macOS
稳定边界 raw syscall 号（最底） Win32 DLL API（ntdll 号不稳） libSystem 符号（号不稳）
可否静态链 libc 直 syscall 可（musl static） 不可（须经 ntdll） 不可（须经 libSystem）
内核结构 宏内核 混合（NT 微内核风 + 大量内核态子系统） 混合（Mach 微内核 + BSD）
异步 I/O 旗舰 io_uring(5.1+) IOCP(2000s) kqueue + GCD
事件多路复用 epoll IOCP/旧 select kqueue

12.2 Windows API ↔ Linux/POSIX 一览

Windows 的机制是用户 API（Win32 的 kernel32/user32）→ 转发到 ntdll.dll 里的 Nt*/Zw* 存根 → 存根把 SSN（System Service Number）放 eax、执行 syscall(x64)/svc(aa64) → 内核经 SSDT（System Service Descriptor Table）查表分发，SSN 每个版本都会变，GUI/GDI 走 Shadow SSDT（win32k）。功能对照（2026：Win11 / Server 2025）：

Windows API 功能 与 Linux/POSIX 的对应
CreateFile/CreateFile2 打开/创建文件、设备、管道 ≈ open，一个 API 覆盖 open+socket+CreateNamedPipe 多职责

VirtualAlloc/VirtualAlloc2 保留/提交虚拟内存页 ≈ mmap(MAP_ANONYMOUS)+mprotect；Reserve/Commit 两段 ≈ 惰性+touch

12.3 macOS API ↔ Linux/POSIX 一览

macOS 的内核 XNU 是 Mach 微内核 + BSD 的混合，是个双内核：BSD syscall 与 Mach trap 共用一条陷入指令但用号区分——aa64 是 svc #0x80、号在 x16，号高字节是 class 前缀（0x2000000|n 是 UNIX/BSD 类走 unix_syscall，负号/0x1000000|n 是 Mach trap 类走 mach_syscall）。用户必须经 libSystem（含真正的 svc 存根），Apple 不保证 syscall 号稳定。功能对照（2026：macOS 15+，Apple Silicon aa64 为主）：

macOS API / 机制 功能 与 Linux/POSIX 的对应
BSD syscall 层(open/read/mmap/fork/execve) POSIX 文件/进程/内存 几乎 1:1 = POSIX（XNU 的 BSD 半边直接源自 4.4BSD），号带 0x2000000 前缀
libSystem.dylib macOS 的 libc(含 libc+libpthread+libm+内核存根) ≈ glibc/musl 角色，但强制经它（不可静态链接绕过）

kqueue(kqueue/kevent) 统一事件通知(fd/信号/定时器/vnode/进程) ≈ epoll，但更通用(一套 API 等 fd+signal+timer+文件变更)，源自 FreeBSD

12.4 跨 OS 运行：wine / WSL / Hyper-V / VMware

知道了三家的稳定边界，就能看懂”在一个 OS 上跑另一个 OS 的程序”有哪几条路。它们恰好落在两个层面：API 翻译（不要另一个内核）和虚拟化（要另一个内核），后者正好接回 §11 的 hypervisor。

wine——Linux 跑 Windows 程序，靠 API 翻译而非虚拟化。Wine 的名字就是递归缩写”Wine Is Not an Emulator”——它不模拟 x86 CPU、不跑 Windows 内核，而是把 Win32/ntdll 那套 API 在 Linux 上重新实现一遍，外加一个 PE/COFF 加载器直接把 .exe 装进 Linux 进程地址空间。一个 Windows 程序调 CreateFile，wine 的 kernel32 实现把它翻译成 Linux 的 open；调 ntdll 的 Nt* 存根，wine 把它落到对应 Linux syscall。Windows 的内核对象（事件、互斥、进程句柄）由一个叫 wineserver 的用户态守护进程统一管理（扮演 NT 内核对象管理器的角色）。这条路的优劣很清楚：没有虚拟化开销、Windows 程序和 Linux 程序共用一个内核，但只要 wine 没实现某个 API 或实现有偏差就会出错。Valve 的 Proton 在 wine 基础上叠加 DXVK/vkd3d（把 Direct3D 翻译成 Vulkan）让 Windows 游戏在 Linux 上跑，是这条路最成功的工业落地。

WSL——Windows 跑 Linux 程序，两代两条路。WSL1 走的是和 wine 对偶的 API 翻译——在 NT 内核里加一个 Linux syscall 翻译层（lxcore），把 Linux 程序发出的 syscall 实时翻译成 NT 原生调用，没有 Linux 内核、没有虚拟化。它的短板和 wine 同源：syscall 覆盖不全、某些行为（尤其文件系统语义、fork 细节）难完美对齐。WSL2 因此换了根本不同的路——在一个基于 Hyper-V 的轻量 utility VM 里跑一个真正的 Linux 内核，于是 syscall 兼容性变成 100%（因为就是真 Linux），代价是引入了一层虚拟化和跨 VM 的文件访问开销。这两代的对比恰好复刻了 §11 容器那条光谱里”API 拦截 vs 真内核”的取舍。

Hyper-V 与 VMware——承载这一切的 hypervisor。Hyper-V 是微软的 type 1 裸金属 hypervisor：它装上后会滑到 Windows 之下，Windows 自己变成一个特权的根分区（root partition），WSL2、Windows Sandbox、Docker Desktop 的 Linux 后端都跑在它之上的 utility VM 里。VMware 则两条产品线都有——Workstation/Player 是 type 2 宿主型（作为普通程序跑在 Windows/Linux 上），ESXi 是 type 1 裸金属（数据中心直接装在硬件上）。把它们和 §11.1 的分类对上：wine/WSL1 是 API 翻译（最轻，无内核），WSL2/microVM 是虚拟化里的轻量 VM，Hyper-V/ESXi 是 type 1，VMware Workstation 是 type 2。补一句跨架构的对偶——Apple Silicon 上的 Rosetta 2 是把 x86-64 二进制翻译成 aa64（AOT 为主、JIT 兜底的二进制翻译），解决的是”跨指令集跑程序”，与 wine/WSL 解决的”跨 OS 跑程序”正交：一个翻译 ISA，一个翻译 API/syscall，组合起来才是完整的”在 A 机器上跑 B 程序”。

13. 系统裁剪与发行版

走到这里，从板级到 libc 到运行时到隔离都讲完了，最后一步是把这些零件组装成一个能启动、能用、能裁剪的完整系统——这就是 rootfs 构建与发行版的工作。本节穷尽本地的五个构建范式：busybox（单二进制塞下整套命令）、buildroot（Make+Kconfig 协调器）、Yocto（元数据 + 任务引擎）、openwrt（路由器专用四件套）、openRuyi 与 ruyi-tutorials（RPM 发行版 + LFS 风手工自举），再讲启动接力与 FHS，最后横向收束。

13.1 五类构建范式定位

先把全景摆出来——同样是”从源码到镜像”，五家在核心机制、输出粒度、增量重建上选择各异：

13.2 busybox：一份声明源，七种语义复用

busybox 是”瑞士军刀”——一个静态二进制内含约 350 个 applet（命令），靠 argv[0]（或 busybox <applet>）选择入口，典型全量约 700KB–1MB 静态。它的设计精髓是 X-macro 单一声明源：applets.src.h 里一份命令清单，靠在 #include 前 #define 不同的展开规则，让同一份清单生成七种产物——函数原型声明、名字↔函数对、帮助文本、符号链接表、suid 表、脚本表、以及核心的 struct bb_applet applets[] 数组。工程价值在于新增一个命令只需在它自己的 .c 顶部写一行 //applet: 注释 + 一段 //config: Kconfig + //usage: 帮助，无需改任何集中清单，这就是”single source of truth”。运行时分发不直接用含字符串指针的结构体数组（浪费 RAM），而是用一个 host 程序在编译期把它压成两张紧凑表——所有名字背靠背 NUL 分隔的大字符串 applet_names[]，加上与之一一对应的函数指针表 applet_main[]，外加把 nofork/noexec/suid/安装位置位压缩进每 applet 几 bit 的属性表。查找用”已知偏移采样表”先把线性查找缩到一段、再逐字节比较（注释甚至给出约 350 applet 下不同采样密度的 cycle 成本表），命中后落到 applet_main[applet_no](argc, argv) 这一句函数指针分发。极致裁剪时若 .config 只选一个 applet，走 SINGLE_APPLET_MAIN 路径连查找表都不链入，可降到几十 KB。

busybox 的 init 是个可作容器/嵌入式 1 号进程的最小 PID 1。它用位掩码定义动作类型（SYSINIT 系统初始化 / WAIT 阻塞等待 / ONCE 跑一次 / RESPAWN 退出即重启 / ASKFIRST 按回车启动 / CTRLALTDEL / SHUTDOWN / RESTART），主流程在极早期就 sigprocmask 屏蔽关机/重读信号（防”用户在 init 极早期发 poweroff”丢信号），校验 getpid()==1，reboot(RB_DISABLE_CAD) 把 Ctrl-Alt-Del 从内核直接重启改成 init 优雅处理，然后核心顺序是 run_actions(SYSINIT)→WAIT→ONCE、最后进永久循环跑 RESPAWN/ASKFIRST 并醒于 SIGCHLD。无 /etc/inittab 时有内建默认（SYSINIT 跑 /etc/init.d/rcS、各虚拟终端 ASKFIRST 起 login shell、SHUTDOWN 时 umount -a -r + swapoff -a）。

13.3 buildroot：Kconfig + per-package .mk + stamp 状态机

buildroot 的哲学是纯 Make + 单一 .config，每个包一个 <pkg>.mk（本地 2953 个包）。每个包 .mk 末尾 $(eval $(generic-package))（或 autotools/cmake/cargo/python/golang 变体），把包名展开成一组以 .stamp_* 空文件为目标的 Make 规则。这些 stamp 就是一台状态机——每个阶段一个 stamp（downloaded→extracted→patched→configured→built→staging_installed→target_installed→installed），Make 用 stamp 的存在/时间戳判断阶段是否完成，规则体统一是 step_start → hooks → 命令 → step_end → touch $@。包描述很声明式，一个 autotools 包就是 XXX_VERSION/XXX_SITE/XXX_SOURCE/XXX_LICENSE/XXX_CONF_OPTS 几行变量加 Kconfig 驱动的可选特性。三个目录要分清：host/ 是 build 机上跑的工具 + 目标工具链 sysroot，staging/ 是带 dev 头文件和库的交叉 sysroot（供其它包编译时链接、不进最终镜像），target/ 是近乎完整的根文件系统（无 dev 头、二进制已 strip、最终镜像源）。工具链有 internal（buildroot 自己从 binutils+gcc 两遍+libc 源码构建）和 external（直接用预编译工具链）两种 backend。打包 rootfs 用 fakeroot——非 root 用户无法 chown root:root/mknod，fakeroot 用 LD_PRELOAD 拦截 stat/chown/mknod 伪装 root，在用户态生成”看起来 root 拥有”的镜像，其中 mkusers 生成 /etc/passwd+shadow+group、makedevs 按设备表造 /dev/* 静态节点，最后落出 ext4/squashfs/cpio 等格式。它的增量重建之弱正源于 stamp——一旦 touch，除非手工 make <pkg>-dirclean/-rebuild，改源不会自动重跑，这是 buildroot 与 Yocto 的关键差异。

13.4 Yocto/Poky：bitbake task DAG + layer + sstate

Yocto 是工业级的元数据 + 任务引擎，三层概念栈：bitbake（Python 任务引擎，解析配置、构建 task DAG、调度执行）→ metadata（recipe .bb / .bbappend / .bbclass / .conf）→ layer（meta-* 目录，关注点分离让 BSP/distro/app 各自成层，叠加靠 .bbappend 而非改原 recipe）。一个 recipe 描述一个包——元数据变量（SRC_URI/LICENSE/DEPENDS/PV）加任务函数，.bbclass 用 inherit 复用任务模板（类比 buildroot 的 *-package 基础设施）。标准 task 链是 do_fetch→do_unpack→do_patch→do_configure→do_compile→do_install→do_populate_sysroot→do_package→do_package_write_{rpm,deb,ipk}→do_rootfs/do_image，与 busybox/buildroot 不同的是每个 task 是独立可缓存单元、task 之间靠 DAG 依赖，且每个 recipe 有独立的 recipe-sysroot（比 buildroot 单一 staging 更隔离、杜绝头文件串味）。它的灵魂是 sstate 签名缓存——每个 task 算一个 signature = basehash（该 task 变量/函数内容的 hash）+ 所有依赖 task 的 hash，把这个完整输入指纹写进 stamp 文件名，任何元数据改动改变 hash 就自动重跑该 task 及下游（这正是 buildroot stamp 做不到的”内容感知”）；task 输出打包进 sstate cache，下次 hash 命中就直接解包产物、跳过 do_compile（setscene 任务）。工程意义是改一行 distro.conf，buildroot 可能要全重，Yocto 只重跑受 hash 影响的子树——这是它工业级可维护口碑的根，代价是 recipe 语言 + 多层 + 签名带来的陡峭学习曲线。

概念 Yocto buildroot 类比
软件描述 recipe .bb package .mk
任务模板 .bbclass + inherit *-package 基础设施
配置 .conf(local/distro/machine) .config(Kconfig)
叠加定制 .bbappend(不改原文件) BR2_GLOBAL_PATCH_DIR/_OVERRIDE_SRCDIR
板支持 meta-<bsp> + machine .conf board/ + <board>_defconfig

13.5 openwrt：procd / ubus / uci 四件套

openwrt 是路由器优化发行版，有四大自研子系统。procd 是它的 PID 1/服务管理器（取代 sysvinit），服务脚本范式是 /etc/init.d/<svc> shell 里设 USE_PROCD=1 + start_service() 里 procd_open_instance/procd_set_param command/procd_set_param respawn/procd_close_instance，这些辅助函数把服务描述序列化成 JSON 经 ubus 交给 procd 守护、由它 fork/监督/respawn。ubus 是 openwrt 版”轻量 D-Bus”——Unix socket + ubusd 守护，服务注册对象/方法，CLI ubus call <obj> <method> '{json}'，procd/netifd/rpcd 全靠它互通。uci（Unified Configuration Interface）是统一配置——/etc/config/<pkg> 纯文本（config/option/list 三关键字），CLI uci get/set/commit，首启动跑 /etc/uci-defaults/* 后 commit 固化，LuCI web UI 即它的图形前端。包管理上 openwrt 有一次迁移值得记：24.10 仍用 opkg（ipkg fork，.ipk = ar 包），切换到 apk（Alpine Package Keeper）发生在 25.12.0（2026-03 发布，主因 opkg 停止维护、apk 活跃），同版还把 wifi 等系统脚本改写为 ucode（JS 风脚本，直连 ubus/uci）；procd/ubus/uci 不受包管理迁移影响。

13.6 openRuyi 与 ruyi-tutorials：RPM 发行版与 LFS 自举

openRuyi 是 ISCAS（中科院软件所）主导的 rv RPM 发行版，结构是 SPECS/<pkg>/<pkg>.spec 标准 RPM spec——许可证用 MulanPSL-2.0（木兰宽松许可证），有 %bcond 条件构建开关、#!RemoteAsset: sha256: 自定义远程资产校验、systemd unit 作 init（对照 openwrt 的 procd、buildroot 默认的 busybox-init），并用新式 RPM 的 BuildSystem: autotools + BuildOption 声明式构建省去手写 %build/%install，走 REUSE 合规（每文件 SPDX 头）。本质是 Fedora/openEuler 风 RPM 工作流移植到 rv。

ruyi-tutorials 是 LFS 风从零自举的教学项目，纯 shell 脚本顺序执行（prepare-env→host-tools→toolchain→opensbi→linux→busybox→sysvinit→coreutils→bash→python3→target-image）。它最有教学价值的是 toolchain 目标的两遍 gcc bootstrap——为什么两遍是个鸡生蛋问题：编 glibc 需要编译器，但完整 gcc 又需要 glibc 提供的 libc/启动文件，所以第 1 遍先 configure 一个 --enable-languages=c --disable-shared --without-headers --with-newlib 的最小 gcc（不依赖目标 libc、只能编 C、无线程无共享库，仅够编出 glibc），用它把 linux-headers + glibc 装进 staging，第 2 遍再 configure 一个 --enable-shared --enable-threads --with-sysroot=staging 的完整 gcc。工具链外面包一层 wrapper（与 buildroot 同源，把真实 riscv64-gcc 改名 *.br_real、gcc 软链到 wrapper 统一注入 sysroot/安全 flag），ARCH/ABI 锁定 rv64imafd_zicsr_zifencei + lp64d。target 阶段同样用 fakeroot 造 rootfs。

13.7 rootfs 启动接力与 FHS

镜像造好后怎么启动？内核解压 → 挂 rootfs → 执行 PID 1，根文件系统有两条路。现代是 initramfs——cpio.gz（或 cpio.zst）打包，内核把它解到 tmpfs 直接当根、执行 /init（PID 1），无需 mount、无块设备依赖（init= 内核 cmdline 可覆盖）。旧式是 initrd——ramdisk 块设备，内核挂载后跑 /linuxrc，它再 pivot_root 到真实根。典型流是内核 → initramfs /init（加载驱动/解密/找真根）→ switch_root → 真实 rootfs /sbin/init。PID 1 的职责不论哪家 init 都一样：系统初始化（挂 /proc /sys /dev、mount fstab、设主机名）、启动并监督服务、收养孤儿进程并 reap（避免僵尸）、处理关机/重启信号。服务管理范式横向：

维度 sysvinit systemd OpenRC procd busybox-init
配置 inittab + init.d shell unit 文件(声明式) init.d + conf.d init.d shell + ubus JSON inittab(极简)
启动模型 runlevel 串行符号链 依赖图并行 + socket 激活 依赖排序可并行 START= 序 + procd 监督 action 位掩码顺序
监督/respawn inittab respawn Restart= 原生 需 supervise-daemon procd_set_param respawn inittab respawn
体量 极小纯 shell 大(含 journald/logind/networkd) 小 小(路由器专用) 最小(嵌入式)
典型用户 老 RHEL/Debian 现代主流(Fedora/Ubuntu/openEuler) Gentoo/Alpine OpenWrt 嵌入式/容器

根文件系统的目录布局由 FHS 3.0（Filesystem Hierarchy Standard）约定：/bin 基础命令、/sbin 系统管理命令、/lib 基础库 + 内核模块、/etc 主机本地配置（纯静态不可执行）、/dev 设备节点、/proc 与 /sys 伪 FS（启动挂载）、/usr 只读可共享次级层级、/var 可变数据、/run 运行期 tmpfs、/tmp 临时、/boot 内核+initramfs+引导器配置。现代趋势是 UsrMerge（openRuyi 等新发行版把 /bin→/usr/bin、/lib→/usr/lib 全软链，简化只读 /usr + 镜像分层），嵌入式（busybox）则常只保留 /bin(busybox+软链)//sbin//etc//dev//proc//sys//tmp//lib 极简骨架。

一句话收束：LFS 教你”为什么”（每步手工，理解 bootstrap），buildroot 给你”最简能用”（Make+Kconfig，stamp 直白但增量弱），Yocto 给你”工业可维护”（task DAG + sstate 内容感知缓存 + 分层，代价是复杂度）。三者并非对立——很多产品 LFS 起步理解、buildroot 原型、Yocto 量产。系统裁剪的通用技法也在这里收口：加法（从零选包）是嵌入式主流，核心手段是 busybox 替 coreutils（一个二进制抵几十工具）、musl 替 glibc（小一半多）、静态链接去动态加载器、strip 去符号、squashfs 压缩只读根、initramfs cpio.gz、删 /usr/share/{man,doc}、locale 只留一个、kmod 只装实际驱动，再极致就是 busybox 单 applet 的几十 KB。这一整套”把通用系统裁到刚好够用”的能力，正是从板级一路讲到这里的终点——一个能在目标硬件上启动、跑起用户程序、又小到塞进 Flash 的完整系统。

16. 思考题（附答案）

问 1：同一个 printf，在 musl、newlib、baselibc 三个 libc 上落地路径有何不同？这说明 libc 的本质是什么？
答：musl 里 vfprintf 累积到 FILE 缓冲、flush 时 writev 进内核；newlib 里经 _write_r 落到一个由 BSP/RTOS 填的 _write 弱符号桩；baselibc 里逐字符走 FILE 的 put 函数指针（可能直接是 UART 寄存器写）。同名同语义、落地三样，说明 libc 的本质是”ISO C/POSIX 语义”与”内核/硬件接口”之间的桥——契约在上，实现可换。

问 2：musl 为什么用 noinline + 空 asm(“memory”) + 符号查找间接调用三种手段反复”钉死”启动期的初始化顺序？
答：因为编译器的内联、寄存器提升、把取址当链接期常量折叠，都会破坏”先初始化 TLS/SSP/重定位、后跑用户代码”的强顺序。noinline 防 init 大栈帧残留整个进程生命周期且防内联重排；空 asm("memory") 是零指令优化屏障，强制 stage2 的副作用排在初始化之后；运行时符号查找让编译器无法跨”运行时不可知的地址”重排被标成 pure/const 的 errno/tp 读取。这是”自举期不能依赖尚未完成的初始化”的经典难题。

问 3：musl 一律 eager binding 而 glibc 默认 lazy binding，各有什么取舍？为什么”lazy 是默认”不是普适事实？
答：glibc lazy 启动快（按需解析）但 GOT 运行期可写、是攻击面，且与 full RELRO 冲突；musl eager 启动时全解析、没有 _dl_runtime_resolve trampoline，配合 full RELRO 天然防 GOT 改写，还省了大量脆弱的架构相关代码，代价是启动时多解析。所以”lazy 是默认”只对 glibc 成立、对 musl 不成立——是个该按实现区分的点。

问 4：Rust 的 core/alloc/std 三层各引入什么前提？为什么说它恰好映射全栈 OS 的固件/引导/应用三级？
答：core 零依赖（只要有 CPU + 编译器，不碰堆不碰 OS）；alloc 加一个全局分配器（解锁堆容器，仍无 OS）；std 加一个宿主 OS（io/fs/net/thread）。映射关系是 M-mode 固件停在纯 core（只用 ptr::write_volatile 操作 MMIO、atomic 抢占、fmt 串口打印），带堆的 bootloader/unikernel 是 core+alloc（挂分配器管页表/镜像），用户态程序是 std（需要内核提供一个 sys::pal 后端落到自家 syscall）。

问 5：为什么不是所有 syscall 都能走 vDSO？__vdso_rt_sigreturn 在 vDSO 里又是为什么？
答：vDSO 只能放纯读硬件状态、不改内核数据结构、不需特权的操作（时钟、CPU 号）；open/write/mmap/clone 都要改内核全局表（fd table/page table/task list），不可能在用户态完成。__vdso_rt_sigreturn 在表里不是性能优化，而是信号返回 trampoline——它必须是内核已知的固定地址，让 handler 跑完能跳回被打断点。

问 6：容器和虚拟机的本质区别是什么？从 runc 的源码层面如何证明”容器不是虚拟化”？
答：容器共享宿主内核、靠 namespace+cgroup+caps+seccomp+LSM 软隔离，虚拟机有独立 guest 内核、靠硬件辅助虚拟化 + 二级地址翻译。源码证明是：runc 全程只调 clone/setns/unshare + 写 cgroupfs + pivot_root + seccomp/capset，没有任何硬件虚拟化指令——容器就是被内核机制框住视野与资源的普通进程。microVM（Firecracker/Kata）才引入 KVM，是容器与 VM 之间的折中。

问 7：buildroot 的 stamp 状态机和 Yocto 的 sstate 签名缓存，在增量重建上为什么一弱一强？
答：buildroot 的 .stamp_* 只记录”这个阶段做没做”（空文件 + 时间戳），改了源码但 stamp 已存在就不会自动重跑，除非手工 dirclean/rebuild——这是”存在性”判断。Yocto 的 sstate 给每个 task 算一个 signature = 内容 basehash + 依赖 hash，写进 stamp 文件名，任何元数据改动改变 hash 就自动重跑该 task 及下游——这是”内容感知”判断。代价是 Yocto 的概念复杂度（recipe 语言 + 多层 + 签名）远高于 buildroot。

问 8：rv 的 J 扩展想优化 JIT 的哪些痛点？为什么 __clear_cache 在 x86 上什么都不做、在 rv 上却要走 syscall？
答：J 扩展（2026 仍 draft）针对动态语言的 GC、boxing、整数溢出检测、icache 管理。icache 是关键痛点——x86 硬件保证 I/D cache 一致（JIT 写完码直接能执行，__clear_cache 无需做事），而 rv 的 fence.i 只对本 hart 有效，多核下别的 hart 的 I-cache 不会被刷到，所以 Linux 把 icache flush 上收为 syscall、由内核发远程 fence.i IPI 同步所有 hart。J 扩展想给 JIT 更轻量的跨 hart 同步原语，以及用 Pointer Masking 让 tagged pointer 近零开销。
